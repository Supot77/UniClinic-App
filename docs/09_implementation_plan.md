# 09. แผนพัฒนา รายการตัดสินใจ และการตรวจรับ

วันที่: 2 กันยายน 2569 (2026-09-02)  
สถานะ: แผนขยายจากฐาน 01–06 และรายการรายละเอียดรอสรุป — ยังไม่เริ่มแก้โค้ดตามแผนนี้

## 1. หลักการเริ่มงาน

ช่วงปัจจุบันทำเอกสารเท่านั้น การระบุผู้รับผิดชอบหรือวันในตารางเป็นการเสนอแผน ไม่ใช่หลักฐานว่ามีการมอบหมายใหม่ เริ่มทำแล้ว หรือทีมตกลงลดขอบเขตแล้ว

ก่อนพัฒนาแต่ละส่วนให้มีข้อยุติของเรื่องที่กระทบส่วนนั้น ข้อตกลงข้อมูลระหว่างผู้รับผิดชอบ และเกณฑ์ยอมรับที่ตรวจได้ เริ่มแก้โค้ดเมื่อเจ้าของโครงการสั่งให้เริ่มระยะพัฒนา

## 2. เรื่องที่ต้องตัดสินใจก่อนล็อกแบบ

ไม่ใช่ทุกเรื่องในตารางเป็นเรื่องที่เอกสารเดิมยังไม่มีคำตอบ ให้ใช้ฐาน 01–06 ต่อไป ส่วนกติกาที่ขยายและข้อเสนอเปลี่ยนฐานยังมีสถานะ **รอสรุป/เสนอ** วันที่และผู้สรุปข้อยุติใหม่ยังไม่ได้กำหนด การปรับเอกสารครั้งนี้ไม่ใช่การอนุมัติข้อเสนอแทนทีม

ใช้ [เอกสาร 10: ประเด็นสำหรับคุยกับทีม](10_team_decisions.md) สำหรับคำถาม ทางเลือก ผู้ร่วมคุย ลำดับประชุม และแบบจดเรื่องค้าง แล้วบันทึกข้อยุติหลักกลับมาในเอกสารนี้

## 4. แผนตามลำดับงาน

คง 4 ระยะและช่วงวันตามไฟล์ 06 ด้านล่างเพิ่มงานส่งต่อและหลักฐานตรวจรับให้ชัดขึ้น แต่ไม่ได้เปลี่ยนแผนเป็นให้สมาชิกทำฟีเจอร์เรียงกันทีละคน การเริ่มพัฒนาจริงยังรอคำสั่งเจ้าของโครงการ และไม่ได้อ้างว่าระยะใดผ่านแล้ว

| ระยะ/เป้าหมาย | งาน | ผู้รับผิดชอบเสนอ | หลักฐานก่อนผ่านระยะ |
| --- | --- | --- | --- |
| 1: วางรากฐาน 1–4 ก.ย. | อ่านฐาน 01–06 ร่วมกัน สรุปรายละเอียดที่ขวางการเริ่มงาน เตรียมโปรเจกต์ Supabase แบบข้อมูล client กลาง types และแนวทางค่าตั้งค่า | หัวหน้าทีม/ฟีม และทุกคนตามไฟล์ 06 | แบบและข้อมูลรับส่งตรงกัน สมาชิกเริ่มระบบได้ มีผู้รับผิดชอบเรื่องค้าง; ยังไม่บังคับให้ฟีเจอร์สมาชิกทั้งหมดเสร็จก่อนระยะ 2 |
| 2: พัฒนาฟีเจอร์ 5–11 ก.ย. | สมาชิกทำส่วนของตนตามขอบเขตครบใน 07 รวม admin ค้นหา ปฏิทิน ผลตรวจ คลัง รอบเตือน และส่วนหน้าศูนย์แจ้งเตือน/แดชบอร์ด | สมาชิกทั้ง 6 คนตามเจ้าของเดิม | แต่ละคนแสดงงานหลักของตนได้ ทดสอบส่วนที่ทำแล้ว และตรวจข้อตกลงเชื่อมข้อมูลโดยมีรายการที่ยังไม่เสร็จชัดเจน |
| 3: เชื่อมระบบและเตือน 12–15 ก.ย. | เชื่อมใบสั่งกับจ่ายยา รอบเตือนกับอีเมล/ข้อความ และข้อมูลจริงกับ Broadcast/แดชบอร์ด รวมงานเข้า dev | ปาย/กัญจน์ กลอง เฮิร์บ และทุกคนร่วมทดสอบตามไฟล์ 06 | เชื่อมข้ามบทบาทได้ มีผลทดสอบสิทธิ์ จอง/จ่ายพร้อมกัน ป้องกันซ้ำ และงานอีเมลรอบ 15 นาที |
| 4: ทดสอบและนำเสนอ 16–18 ก.ย. | 16 ก.ย. ทดสอบครบกระบวนการ; 17 ก.ย. แก้ข้อผิดพลาด/หน้าจอและรวม main; 18 ก.ย. เตรียมข้อมูลและซ้อมนำเสนอตามแผนเดิม | ทุกคน | ตรวจ AC01–38 ที่ปรับตามข้อยุติแล้ว บันทึกผลจริง ตรวจ lint/typecheck/build และเตรียมหลักฐาน/ข้อจำกัดสำหรับนำเสนอ |

ทีมพัฒนาคนละฟีเจอร์ได้หลังตกลงข้อมูล โดยเชื่อมเป็นช่วง เช่น ตรวจรูปแบบใบสั่งก่อนส่งให้หน้าจ่ายยา ผู้ตรวจและวันส่งต่อย่อยให้ตกลงใน D16 หากต้องเลื่อนฟีเจอร์ที่อยู่ในไฟล์ 02 ต้องบันทึกการเปลี่ยนขอบเขต D02 ก่อน ไม่ถือว่ารายการนั้นเป็นส่วนเสริมเพียงเพราะเอกสารร่างก่อนหน้าเคยเสนอให้เลื่อน

งานที่ต้องเห็นในระยะ 2–3 เพิ่มจากร่างก่อนหน้า: ค้นหาผู้ป่วยและ admin (ฟีม), ปฏิทินและการลบแพทย์/แผนกตามกติกา (ช้อป), สถานะคิวของ staff (ปาย), เปิด/แก้/ระงับข้อมูลยา (กัญจน์), ปิด/ลบรายการเตือนและ missed (กลอง), Broadcast/ลบข้อความ/สถิติแผนก/สรุปแพทย์ (เฮิร์บ)

## 5. ข้อตกลงส่งต่องานระหว่างสมาชิก

| ผู้ส่ง → ผู้รับ | สิ่งที่ต้องตกลงก่อนเชื่อม |
| --- | --- |
| ฟีม → ทุกคน | รูปแบบผู้ใช้/บทบาท สถานะกำลังโหลด/หมดอายุ วิธีรับข้อผิดพลาด และสิทธิ์แต่ละงาน |
| ช้อป → ปาย | รหัสแพทย์/รอบ วันเวลาไทย ความจุ สถานะรอบ และเงื่อนไขเปิดรับ |
| ปาย → กัญจน์ | รหัสผลตรวจ/ใบสั่ง/รายการยา ผู้ป่วย จำนวน วิธีใช้ และเวลาที่ใบพร้อมจ่าย |
| กัญจน์ → ปาย/เฮิร์บ | ผลยืนยันจ่ายที่ทำซ้ำได้ ยอดก่อน/หลัง และสถานะกรณีไม่สำเร็จ |
| กลอง → เฮิร์บ | รหัสมื้อ ผู้รับ เวลา และเหตุการณ์ที่สร้างข้อความหนึ่งครั้ง |
| ทุกคน → เฮิร์บ | นิยามตัวเลข แหล่งข้อมูล และสิทธิ์ที่ใช้คำนวณ ไม่ส่งตัวเลขตัวอย่างเป็นผลจริง |

คำสั่งที่เปลี่ยนข้อมูลควรมีผลสำเร็จและรหัสเหตุผลที่ตกลงร่วมกัน เช่น คิวเต็ม ไม่มีสิทธิ์ สต๊อกไม่พอ หรือทำรายการแล้ว พร้อมข้อความไทยสำหรับแสดงผล รหัสและรูปแบบสุดท้ายให้บันทึกก่อนสร้างบริการที่แต่ละคนจะเรียก

## 6. เอกสารและการทำงานร่วมกัน

- คงการแบ่งเจ้าของฟีเจอร์และกฎไม่แก้พื้นที่เพื่อนตามไฟล์ 05 รวมถึง feature → dev → main การเพิ่มข้อยกเว้นแก้ไฟล์กลางผ่านผู้ตรวจเป็นรายละเอียด D16 ที่ต้องตกลง ไม่ตีความว่าเอกสารนี้อนุญาตข้ามกฎเดิมแล้ว
- หากเลือกเปลี่ยน schema ให้ปรับ ER/Data Dictionary และข้อตกลงข้อมูลในเอกสารก่อน แล้วค่อยทำ migration ในระยะพัฒนา
- หลังเริ่มใช้ฐานข้อมูลร่วมกัน ให้เพิ่ม migration ใหม่แทนแก้ประวัติเดิมโดยไม่มีการตกลง และไม่รัน SQL เปลี่ยนฐานข้อมูลจริงจากการแก้เอกสาร
- คู่มือเริ่มระบบในอนาคตต้องระบุรุ่นเครื่องมือ วิธีติดตั้ง ลำดับ migrations วิธีสร้างบัญชีทดสอบ และวิธีตรวจผล
- `.env.example` ในอนาคตใส่เฉพาะชื่อค่าและตัวอย่างที่ไม่ใช่ความลับจริง แยกค่าที่ browser อ่านได้จากค่าสำหรับระบบฝั่ง server; ปัจจุบันยังไม่สร้างไฟล์นี้เพราะงานครั้งนี้จำกัดที่ .md ใน docs
- ไม่ใช้การไม่มี error จาก lint เป็นหลักฐานว่าการจอง สิทธิ์ หรือการจ่ายยาถูกต้อง ต้องมีผลตาม AC ที่สัมพันธ์กัน

## 7. แบบบันทึกข้อยุติ

คัดลอกส่วนนี้ภายในเอกสารเมื่อมีการตกลงเรื่องใหม่ แต่ละรายการต้องมีเจ้าของและผลกระทบต่อเอกสารอื่น

| ช่อง | ข้อมูลที่ต้องกรอก |
| --- | --- |
| รหัส | Dxx หรือรหัสใหม่ที่ไม่ซ้ำ |
| เรื่อง/ปัญหา | เหตุผลที่ต้องตัดสินใจ |
| ประเภท | ฐานเดิม / รายละเอียดรอสรุป / ข้อเสนอเปลี่ยนฐาน |
| แหล่งอ้างอิงเดิม | ไฟล์ 01–06 และหัวข้อที่ระบุไว้ หรือระบุว่าเอกสารเดิมยังไม่ลงรายละเอียด |
| สิ่งที่เปลี่ยนจากฐาน | ก่อน/หลังและเหตุผล; ถ้าเพียงเติมรายละเอียดให้ระบุชัด |
| ข้อยุติ | พฤติกรรมหรือขอบเขตที่เลือก |
| ผลกระทบ | หน้าจอ ฐานข้อมูล สิทธิ์ และสมาชิกที่เกี่ยวข้อง |
| เอกสารที่ต้องแก้ | ชื่อไฟล์ใน docs และหัวข้อ |
| ผู้สรุป/วันที่ | เติมเมื่อมีข้อยุติจริง |
| สถานะ | เสนอ / ตกลงแล้ว / พัฒนาแล้ว / ตรวจรับแล้ว |
| เกณฑ์ยอมรับ | รหัส AC หรือเกณฑ์ใหม่ที่ตรวจได้ |
| หลักฐาน | ลิงก์ผลทดสอบหรือบันทึกที่เกี่ยวข้องเมื่อมีจริง |

| รหัส AC | สภาพแวดล้อม/ข้อมูลทดสอบ | ผลที่เกิดจริง | ผ่าน/ไม่ผ่าน/ยังไม่ทดสอบ | หลักฐาน/ผู้ตรวจ/วันที่ |
| --- | --- | --- | --- | --- |

## 9. งานเอกสารรอบนี้เสร็จเมื่อ

- มีคู่มืออ่าน ขอบเขต กติกา และแผนที่อ้างอิงกันได้
- ข้อเสนอไม่ถูกระบุว่าเป็นข้อยุติหรือฟีเจอร์ที่ทำเสร็จแล้ว
- มีรายการประเด็นที่ทีมต้องตกลงและเกณฑ์ยอมรับสำหรับงานสำคัญ
- ไฟล์ที่เพิ่มหรือแก้ในรอบนี้เป็น `.md` ภายใน `docs` เท่านั้น

รายการนี้เป็นเกณฑ์งานเอกสาร ไม่ใช่เกณฑ์ว่าระบบคลินิกพัฒนาเสร็จแล้ว
