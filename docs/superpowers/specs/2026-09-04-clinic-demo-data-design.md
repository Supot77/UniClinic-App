# แบบออกแบบข้อมูลจำลองคลินิกมหาวิทยาลัย

วันที่: 4 กันยายน 2026  
สถานะ: ช้อปอนุมัติแบบออกแบบแล้ว; การเปลี่ยน Schema กลางต้องให้หัวหน้าทีมและเจ้าของโมดูลที่เกี่ยวข้องรับทราบก่อนเริ่มพัฒนา

## 1. เป้าหมาย

สร้างข้อมูลสังเคราะห์สำหรับคลินิกมหาวิทยาลัยขนาดเล็ก เพื่อให้สมาชิกทั้ง 6 คนพัฒนาและทดสอบระบบจากข้อมูลชุดเดียวกัน โดยไม่อ้างอิงการดำเนินงานหรือข้อมูลบุคคลของคลินิกจริง

ชุดข้อมูลต้องรองรับเส้นทางตั้งแต่ล็อกอิน จองคิว จัดตารางแพทย์ ตรวจรักษา ออกใบสั่งยา จ่ายยา ตั้งเตือนกินยา รับการแจ้งเตือน และดู Dashboard

## 2. ขอบเขตและสิ่งที่ไม่ทำ

### อยู่ในขอบเขต

- บัญชี Auth ที่ล็อกอินได้จริงครบ 5 บทบาท
- แผนกบริการ 4 แผนก ผู้ให้บริการ 6 คน และหน่วยเภสัชกรรม 1 คน

- บันทึกผลตรวจ ใบสั่งยา คลังยา รอบเตือน การแจ้งเตือน และข้อมูลที่ใช้คำนวณ Dashboard
- Bootstrap ที่รันซ้ำได้และแก้เฉพาะข้อมูลเดโม
- Scenario Catalog สำหรับทดสอบข้ามโมดูล

### ไม่อยู่ในขอบเขตรุ่นแรก

- ข้อมูลจริงของคลินิกมหาวิทยาลัย
- ผู้ป่วย walk-in
- การแบ่งจ่ายยาและการคืนยา
- ยาภายนอกคลินิกที่ผู้ป่วยพิมพ์ชื่อเอง
- ตารางเวรแบบลากวางหรือกฎเวรซ้ำในฐานข้อมูล
- เลขใบประกอบวิชาชีพและระบบห้องตรวจ
- การส่งอีเมลจริงระหว่าง Bootstrap
- ระบบหลายสาขาหรือหลายเขตเวลา

## 6. กติกาการจอง

- ผู้ป่วยจองล่วงหน้าได้ 1–14 วัน
- การจองใหม่มีสถานะ `pending` และกันความจุทันที
- Staff/Admin อนุมัติเป็น `confirmed` หรือปฏิเสธเป็น `rejected`
- ผู้ป่วยยกเลิกเองได้ก่อนเวลาเริ่มอย่างน้อย 2 ชั่วโมง
- `cancelled` และ `rejected` คืนความจุเพียงครั้งเดียว
- ผู้ป่วยจองรอบเดิมซ้ำหรือมีนัดเวลาทับกันไม่ได้
- รอบอดีต รอบเต็ม และรอบปิดรับจองไม่ได้
- `pending`, `confirmed`, `in_progress`, `completed` และ `no_show` ใช้ความจุ ส่วน `cancelled` และ `rejected` ไม่ใช้ความจุ
- Staff เปลี่ยน `confirmed` เป็น `in_progress` และเปลี่ยนเป็น `completed` หลังมีผลตรวจ
- Staff/Admin เปลี่ยน `confirmed` เป็น `no_show` ได้หลังเวลาสิ้นสุดรอบ
- เมื่อแพทย์งดตรวจ Staff เปลี่ยนรอบเป็น `closed` เก็บนัดเดิมไว้ และแจ้งผู้ป่วยที่เกี่ยวข้อง

## 9. การเปลี่ยน Schema กลาง

### Department และ Doctor

เพิ่ม `is_active boolean not null default true` ใน `departments` และ `doctors`

- แพทย์หนึ่งคนสังกัดหนึ่งแผนกในรุ่นแรก
- ข้อมูลที่ไม่เคยถูกอ้างอิงลบถาวรได้
- ข้อมูลที่มีประวัติแล้วใช้การปิดใช้งาน
- รายการปิดใช้งานยังปรากฏในประวัติเก่า แต่ใช้สร้างรอบใหม่ไม่ได้
- การปิดแพทย์ไม่ลบรอบหรือนัดเดิม และ Staff ต้องตัดสินใจเรื่องรอบอนาคตแต่ละรอบ

### Medical Record และสถานะจ่ายยา

เพิ่มฟิลด์ต่อไปนี้ใน `medical_records`:

```text
dispense_status: none | pending | dispensed
dispensed_at: timestamptz nullable
dispensed_by: uuid nullable -> profiles.id
```

ผลตรวจที่ไม่มีรายการยามีสถานะ `none` ผลตรวจที่มีรายการยามีสถานะ `pending` และเปลี่ยนเป็น `dispensed` หลังธุรกรรมจ่ายยาสำเร็จเท่านั้น

เพิ่ม `medical_record_id uuid nullable -> medical_records.id` ใน `inventory_logs` เพื่อให้ตรวจสอบได้ว่าการตัดสต๊อกแต่ละรายการเกิดจากใบสั่งยาใด การปรับยอด รับเข้า และตัดของเสียที่ไม่เกี่ยวกับใบสั่งยาใช้ค่า `null`

### รหัสสำหรับตรวจคำเตือนแพ้ยา

คง `profiles.allergies` สำหรับข้อความที่แสดงต่อผู้ใช้ และเพิ่มข้อมูลที่ระบบเปรียบเทียบได้:

```text
profiles.allergy_codes: text[] not null default '{}'
medications.contraindication_allergy_codes: text[] not null default '{}'
```

ข้อมูลเดโมใช้รหัสอย่างน้อย `PENICILLIN`, `NSAID` และ `LATEX` ก่อนบันทึกใบสั่งยา ระบบหาจุดตัดของรหัสผู้ป่วยกับรหัสของยา ถ้าพบต้องแสดงรายการที่ขัดแย้งและไม่บันทึกจนกว่าแพทย์จะนำยานั้นออกจากใบสั่งยา ข้อความ `allergies` เพียงอย่างเดียวไม่ใช้ตัดสินอัตโนมัติ

### Medication Reminder

เพิ่มฟิลด์ต่อไปนี้ใน `medication_reminders`:

```text
source: manual | prescription
medical_record_id: uuid nullable -> medical_records.id
```

หนึ่งคู่ `(medical_record_id, medication_id)` สร้าง Reminder จากใบสั่งยาได้หนึ่งรายการ การสร้างแบบ `manual` เลือกยาได้เฉพาะจากรายการยาของคลินิก

## 10. กฎความถูกต้องของ Department, Doctor และ Slot

- ชื่อแผนกห้ามซ้ำ
- `start_time < end_time`
- `max_capacity > 0`
- `0 <= booked_count <= max_capacity`
- แพทย์คนเดียวกันมีรอบเวลาทับกันไม่ได้
- แพทย์หรือแผนกที่ปิดใช้งานสร้างรอบใหม่ไม่ได้
- รอบอดีตเปิดรับการจองไม่ได้
- เมื่อ `booked_count = max_capacity` สถานะต้องเป็น `full`
- รอบ `closed` ไม่กลับเป็น `available` โดยอัตโนมัติเมื่อมีการยกเลิกนัด
- ฐานข้อมูลบังคับกฎสำคัญ และ Service แปลงข้อผิดพลาดเป็นข้อความภาษาไทยที่ผู้ใช้เข้าใจได้

## 11. การจ่ายยาแบบครบทั้งใบ

เภสัชกรจ่ายยาครบทั้งใบเท่านั้น ระบบไม่รองรับแบ่งจ่ายในรุ่นแรก

ขั้นตอนจ่ายยาทำใน Database Transaction เดียว:

1. ตรวจว่าผู้เรียกเป็น `pharmacist` หรือ `admin`
2. ตรวจว่าใบสั่งยายังเป็น `pending`
3. ตรวจว่ายาทุกรายการเปิดใช้งานและไม่หมดอายุ
4. ตรวจว่าจำนวนเป็นจำนวนเต็มบวกและสต๊อกเพียงพอทุกตัว
5. ตัดสต๊อกยาทุกรายการ
6. สร้าง `inventory_logs` ที่อ้างอิงการจ่ายครั้งนั้น
7. เปลี่ยนสถานะเป็น `dispensed` พร้อม `dispensed_at` และ `dispensed_by`

ถ้าขั้นตอนใดล้มเหลว ธุรกรรมทั้งหมดต้องย้อนกลับ ใบเดิมที่จ่ายสำเร็จแล้วกดจ่ายซ้ำไม่ได้

## 12. Reminder แบบ Hybrid

หลังใบสั่งยาเปลี่ยนเป็น `dispensed` ระบบเสนอให้ผู้ป่วยสร้าง Reminder จากใบสั่งยา โดยดึงชื่อยา ขนาดยา ความถี่ และจำนวนวันมาแสดง ผู้ป่วยเลือกเวลาเตือนจริงและยืนยันการสร้าง

- ข้อมูลคำสั่งใช้จากคลินิกแก้โดยผู้ป่วยไม่ได้
- ผู้ป่วยแก้เวลาเตือนและสถานะเปิด–ปิดได้
- การแก้ Reminder ไม่เปลี่ยนใบสั่งยาหรือประวัติการจ่ายยา
- ประวัติ `taken` และ `missed` เดิมไม่ถูกลบเมื่อเปลี่ยนเวลาในอนาคต
- มื้อในอนาคตเป็น `pending` และไม่นับเป็น `missed`
- Peter มีรอบ `active` เวลา 08:00 และ 20:00 พร้อมประวัติย้อนหลัง 3 วัน
- Bruce มีรอบ `paused` สำหรับทดสอบการเปิด–ปิด

| Staff | จัดการแผนก แพทย์ รอบตรวจ และสถานะคิว |
| Doctor | ดูตารางและคิวที่เกี่ยวข้อง และบันทึกผลตรวจของนัดที่รับผิดชอบ |
| Pharmacist | อ่านเฉพาะข้อมูลผู้ป่วยและรายการยาที่จำเป็นต่อการจ่ายยา |
| Admin | จัดการข้อมูลและตรวจสอบทุกส่วน |

เภสัชกรไม่อ่าน `medical_records` ทั้งแถว ระบบมี View หรือ RPC สำหรับคิวจ่ายยาที่คืนเฉพาะ:

```text
medical_record_id
appointment_id
patient_id
patient_name
allergies
prescribed_medications
dispense_status
created_at
```

RPC จ่ายยาตรวจสิทธิ์และข้อมูลอีกครั้งในฐานข้อมูล ไม่เชื่อผลตรวจจากหน้าจอเพียงอย่างเดียว

## 14. Notification และ Dashboard

### Notification

- ผู้ป่วยได้รับ In-app Notification เมื่อ Staff อนุมัติ ปฏิเสธ หรือยกเลิกนัด
- ผู้ป่วยที่เกี่ยวข้องได้รับแจ้งเมื่อรอบถูกปิด
- ผู้ป่วยได้รับแจ้งเมื่อจ่ายยาเสร็จ
- Seed มี Broadcast หนึ่งข้อความ รายการอ่านแล้วหนึ่งรายการ และยังไม่อ่านหนึ่งรายการ
- Bootstrap ไม่ส่งอีเมลจริง Email Worker ใช้โหมด Dry Run และเขียนผลลง Log ของ Worker ระหว่างการทดสอบ โดยไม่เพิ่มตารางประวัติการส่งในรุ่นแรก

### สูตร Dashboard

- นัดหมายวันนี้: รอบวันนี้ทุกสถานะยกเว้น `cancelled` และ `rejected`
- ภาระงานแต่ละแผนก: จำนวนครั้งรับบริการในช่วงที่เลือก ยกเว้น `cancelled` และ `rejected`
- แพทย์ตรวจแล้ววันนี้: จำนวน `completed` แยกตามแพทย์
- คิวคงเหลือ: จำนวน `confirmed` และ `in_progress`
- รอจ่ายยา: จำนวนผลตรวจที่ `dispense_status = pending`
- ยาใกล้หมด: ยาที่เปิดใช้งานและ `stock <= min_stock`
- ยาหมดอายุ: แสดงแยกจากยาใกล้หมด
- สัดส่วนสถานะนัด: นับแต่ละสถานะแยกกัน

Dashboard คำนวณจากข้อมูลต้นทางและไม่เก็บตัวเลขสรุปใน Seed

## 15. หน้าจอในขอบเขตของช้อป

### หน้าจัดการแผนกและแพทย์

- แท็บแผนก: ค้นหา เพิ่ม แก้ไข ลบหรือปิดใช้งาน
- แท็บแพทย์: กรองตามแผนก เพิ่มแพทย์ กำหนดความเชี่ยวชาญ ลบหรือปิดใช้งาน
- ซ่อนรายการปิดใช้งานตามค่าเริ่มต้นและมีตัวกรองดูย้อนหลัง
- การลบหรือปิดใช้งานมีหน้าต่างยืนยันและบอกผลกระทบ

### หน้าปฏิทินตารางตรวจ

- มุมมองรายสัปดาห์เป็นค่าเริ่มต้น
- กรองตามแผนก แพทย์ และสถานะรอบ
- สร้าง ดู แก้ไข และปิดรอบ
- แสดงเวลา แพทย์ แผนก จำนวนจอง/ความจุ และสถานะ
- `available`, `full` และ `closed` ใช้สีต่างกัน
- ไม่มี Drag-and-drop ในรุ่นแรก
- มือถือใช้รายการเรียงตามวัน

หน้าจองคิวเป็นของปายและใช้รหัสแพทย์ รหัสรอบ วันเวลาไทย ความจุ สถานะ และเงื่อนไขเปิดรับจากโมดูลช้อป

## 16. Bootstrap สำหรับ Supabase ร่วม

ทีมใช้ Supabase ออนไลน์ร่วมกันหนึ่งโปรเจกต์ หัวหน้าทีมเป็นผู้ถือ `service_role` และรัน Bootstrap จากเครื่องของตน สมาชิกได้รับเฉพาะบัญชีเดโม

ลำดับ Bootstrap:

1. Auth Users
2. Profiles และ Roles
3. Departments
4. Doctors และสังกัดแผนก
5. Medications และยอดสต๊อก
6. Appointment Slots แบบวันที่สัมพันธ์กับวันรัน
7. Appointments
8. Medical Records และใบสั่งยา
9. Inventory Logs
10. Medication Reminders และ Logs
11. Notifications และข้อมูลต้นทางสำหรับ Dashboard

Bootstrap ต้อง:

- ใช้ Admin API สร้าง Auth User และยืนยันอีเมลสำหรับเดโม
- หา Auth User เดิมด้วยอีเมลและใช้ `user_id` เดิมเมื่อรันซ้ำ
- ใช้รหัสคงที่สำหรับข้อมูลธุรกิจและ `upsert` ข้อมูลเดโม
- คำนวณวันย้อนหลัง 7 วัน วันนี้ และล่วงหน้า 14 วันด้วย `Asia/Bangkok`
- เปลี่ยนเฉพาะบัญชีและรหัสเดโมที่ระบุใน Catalog
- ไม่ล้างฐานข้อมูลทั้งโปรเจกต์
- รายงานจำนวน `created`, `updated`, `skipped` และ `failed`
- ไม่แสดง Secret หรือรหัสผ่านใน Log

`service_role` เก็บใน Environment ของเครื่องหัวหน้าทีม ไม่อยู่ในโค้ดฝั่งเว็บ ไม่ commit และไม่แจกให้สมาชิก

## 18. การตรวจสอบและเกณฑ์พร้อมใช้งาน

### Bootstrap

- พบ Auth/Profile 17 บัญชี แผนก 4 แผนก แพทย์ 6 คน เภสัชกร 1 คน ผู้ป่วย 8 คน และยา 7 รายการ
- มีรอบตรวจและข้อมูลข้ามโมดูลตามช่วงเวลาที่กำหนด
- รันซ้ำแล้วไม่สร้างข้อมูลซ้ำและไม่กระทบข้อมูลนอกชุดเดโม

### ฐานข้อมูลและธุรกรรม

- ปฏิเสธรอบทับซ้อน เวลาไม่ถูกต้อง และความจุไม่ถูกต้อง
- การจองพร้อมกันไม่เกินความจุ
- การจ่ายยาที่ไม่ผ่านเงื่อนไขย้อนกลับทั้งธุรกรรม
- ใบสั่งยาเดิมจ่ายซ้ำไม่ได้
- การปิดแผนกหรือแพทย์ไม่ทำลายประวัติ

### สิทธิ์

- บัญชีทั้ง 5 บทบาทอ่านและแก้ได้เฉพาะขอบเขตของตน
- เภสัชกรไม่เห็นรายละเอียดการวินิจฉัยที่ไม่จำเป็น
- ผู้ใช้ทั่วไปเปลี่ยน Role ของตนเองไม่ได้

### เส้นทางใช้งาน

- SCN-01 ถึง SCN-07 ให้ผลตาม Catalog
- หน้าจอรองรับ Loading, Empty State และข้อความผิดพลาด
- ใช้งานฟอร์มหลักด้วยคีย์บอร์ดและบนหน้าจอมือถือได้

ชุดข้อมูลถือว่าพร้อมให้ทีมเริ่มพัฒนาเมื่อ Bootstrap, ข้อจำกัดฐานข้อมูล, RLS และ Scenario Catalog ผ่านเกณฑ์ข้างต้น

## 19. ลำดับการเริ่มงานร่วมกัน

1. หัวหน้าทีมและเจ้าของโมดูลรับรอง Schema และสัญญาข้อมูลกลางฉบับนี้
2. ทำ Migration สำหรับฟิลด์ ข้อจำกัด View/RPC และ RLS ที่อนุมัติ
3. ทำ Bootstrap และตรวจข้อมูลด้วยบัญชีครบทุกบทบาท
4. ตรึงชนิดข้อมูลกลางและสัญญาส่งต่อระหว่างโมดูล
5. สมาชิกพัฒนา UI และ Service ของตนโดยใช้ SCN-01 ถึง SCN-07 เป็นเกณฑ์ร่วม
