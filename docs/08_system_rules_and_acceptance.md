# 08. กติกาของระบบและเกณฑ์ยอมรับที่เสนอ

วันที่: 2 กันยายน 2569 (2026-09-02)  
สถานะ: แบบร่างสำหรับตกลงก่อนพัฒนา — ยังไม่ใช่พฤติกรรมที่ยืนยันว่าระบบทำได้แล้ว

อ่านร่วมกับ [ขอบเขตโครงการ](07_foundation_and_scope.md) และ [รายการตัดสินใจ](09_implementation_plan.md)

## วิธีแยกฐานเดิมกับกติกาที่เสนอเพิ่ม

ฐานจาก 01–06 ได้แก่ 5 บทบาท การอนุมัติ/ปฏิเสธนัดโดยเจ้าหน้าที่ คิวที่เจ้าหน้าที่เปลี่ยนสถานะได้ การสั่งยาโดยแพทย์และจ่ายโดยเภสัชกร แบบ 11 ตารางที่เก็บรายการยาเป็น JSON ตลอดจนปฏิทิน Broadcast การลบแจ้งเตือน และรอบตรวจเตือน 15 นาที

รายละเอียดที่เพิ่มในเอกสารนี้ เช่น ขอบเขตสิทธิ์อ่านรายช่อง การกันคิว pending เส้นตายยกเลิก การจ่ายครบใบ และกติกาประวัติย้อนหลังยังเป็นร่างตาม D03/D04/D09/D12–D14 ห้ามถือว่าทีมตกลงแล้วเพียงเพราะเขียนเป็นกติกาหรือ AC การเปลี่ยนวิธีเก็บข้อมูลเป็นตารางใหม่ต้องแยกบันทึกเป็นข้อเสนอเปลี่ยนฐาน

## 1. เส้นทางหลักที่จะใช้ตรวจรับ

1. ผู้ป่วยสมัครและเข้าสู่ระบบได้พร้อมโปรไฟล์ หากเลือกเปิดยืนยันอีเมลต้องรองรับขั้นตอนนั้นได้ครบ
2. เจ้าหน้าที่เตรียมแพทย์และรอบเวลาที่เปิดรับ
3. ผู้ป่วยจอง เจ้าหน้าที่อนุมัติ และรายการปรากฏในคิวของแพทย์
4. เจ้าหน้าที่จัดสถานะคิวตามหน้าที่ แพทย์ตรวจและบันทึกผลพร้อมรายการยา สิทธิ์ที่แพทย์จะเปลี่ยนสถานะเองด้วยให้สรุปใน D03
5. เภสัชกรเปิดรายการรอจ่าย ยืนยันจ่าย และตรวจยอดยากับประวัติได้
6. ผู้ป่วยตั้งรอบเตือนเอง ระบบสร้างมื้อยาและแจ้งเตือนตามเวลา
7. ผู้ป่วยบันทึกกินแล้ว เจ้าหน้าที่ใช้กล่องแจ้งเตือน/Broadcast และตัวเลขภาพรวมกับคิวแพทย์แสดงข้อมูลตรงกับรายการจริง

ต้องตรวจทั้งกรณีสำเร็จและกรณีปฏิเสธรายการ การซ่อนปุ่มไม่ใช่หลักฐานว่าบัญชีนั้นถูกห้ามทำรายการจริง

## 2. ตารางสิทธิ์ที่เสนอ

คำว่า “ของตน” หมายถึงเจ้าของข้อมูล ส่วน “ที่รับผิดชอบ” หมายถึงมีความสัมพันธ์กับนัดหรือใบสั่งยาที่กำลังให้บริการจริง

ตารางนี้เป็นข้อเสนอเติมรายละเอียดสิทธิ์ การจำกัดแพทย์/เภสัชกร/ผู้ดูแลให้เห็นเฉพาะข้อมูลบางส่วนต้องสรุป D09 โดยคงหน้าที่ที่ไฟล์ 02 ระบุอยู่แล้ว รายการเพิ่มเติมใต้ตารางเป็นส่วนหนึ่งของขอบเขตเดิมและต้องอ่านร่วมกัน

สิทธิ์ฐานเดิมที่ต้องรวมเพิ่มเติมจากตาราง:

- ผู้ดูแลสร้าง/แก้ข้อมูลผู้ใช้และกำหนดบทบาทได้ ตาม User Story ของ admin ไม่ใช่เพียงจัดการบัญชีตนเอง
- เจ้าหน้าที่เปลี่ยนสถานะคิวรอตรวจ/กำลังตรวจ/ตรวจเสร็จ/ไม่มาได้ตามไฟล์ 02 ส่วนเงื่อนไขเปลี่ยนแต่ละขั้นต้องสรุปกับแพทย์
- เจ้าหน้าที่ส่ง Broadcast ไปยังกลุ่มเป้าหมายได้ เป็นฟีเจอร์เดิม ไม่ใช่ความสามารถที่จะพิจารณาเพิ่มภายหลัง
- ผู้ป่วยลบข้อความของตน และปิดหรือลบรายการเตือนของตนได้ตามไฟล์ 02 รูปแบบลบ/เก็บประวัติต้องสรุปให้ตรงกัน

การสร้างแจ้งเตือนอัตโนมัติเป็นสิทธิ์ของงานระบบที่ตรวจสอบได้ ส่วน Broadcast ตรวจสิทธิ์เจ้าหน้าที่และกลุ่มผู้รับแยกต่างหาก ไม่เปิดให้บัญชีทั่วไปส่งข้อความหาผู้ใช้ใดก็ได้

หากข้อมูลสาธารณะของแพทย์เก็บร่วมใน `profiles` ให้เปิดเฉพาะชื่อและรายละเอียดที่ต้องใช้จอง ไม่เปิดทั้งแถวที่มีข้อมูลส่วนบุคคลเพื่อแก้ปัญหาหน้ารายชื่อแพทย์อ่านข้อมูลไม่ได้

## 3. สมาชิกและการควบคุมสิทธิ์

- สมัครด้วย Email/Password ผ่าน Supabase Auth และกำหนดบทบาทเริ่มต้นเป็น `patient` จากฝั่งที่ผู้ใช้แก้เองไม่ได้
- สร้างโปรไฟล์ด้วยกระบวนการที่ทำงานได้แม้ยังรอยืนยันอีเมล เสนอใช้ database trigger ที่ควบคุมข้อมูลนำเข้าและบทบาท ไม่พึ่งการ insert จาก browser ที่ยังไม่มี session
- ข้อมูลชื่อและช่องโปรไฟล์ที่อนุญาตอาจรับจากผู้ใช้ แต่ห้ามเชื่อบทบาทที่ส่งจากแบบฟอร์มหรือ metadata ที่ผู้ใช้แก้ได้
- การแก้โปรไฟล์ต้องกำหนดรายชื่อช่องที่แก้ได้ ไม่รับแถวทั้งหมดรวม `id`, `role` และข้อมูลระบบ
- การเปลี่ยนบทบาทต้องตรวจผู้กระทำและเก็บประวัติว่าใครเปลี่ยนบัญชีใด จากบทบาทใดเป็นอะไร เมื่อไร
- นโยบายอ่าน `profiles` ต้องไม่วนกลับมาตรวจสิทธิ์ผ่านตัวเอง หากใช้ฟังก์ชันช่วยที่มีสิทธิ์สูง ต้องจำกัดหน้าที่ เจ้าของฟังก์ชัน `search_path` และสิทธิ์เรียกให้เหมาะสม
- การเข้าสู่หน้าเฉพาะบทบาทต้องสอดคล้องกับ RLS/สิทธิ์ของการทำรายการ การตรวจในเมนูหรือ layout อย่างเดียวไม่เพียงพอ
- แสดงข้อผิดพลาดเมื่อโหลดโปรไฟล์ไม่ได้ ไม่ตีความทุกข้อผิดพลาดเป็น “ไม่ได้ล็อกอิน” หรือเก็บข้อมูลผู้ใช้คนเดิมค้างไว้

หลักการจำกัดแถวและคอลัมน์อ้างอิง [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security) และ [Column Level Security](https://supabase.com/docs/guides/database/postgres/column-level-security) ส่วนกรณีสมัครแล้วยังไม่มี session อ้างอิง [signUp](https://supabase.com/docs/reference/javascript/auth-signup)

## 4. รอบเวลาและสถานะนัดหมาย

ไฟล์ 02 ให้เจ้าหน้าที่เปลี่ยนสถานะคิวได้อยู่แล้ว ตารางถัดไปคงหน้าที่นั้นไว้ พร้อมแยกข้อเสนอให้แพทย์เปลี่ยนสถานะเอง รายละเอียดเวลาตัดรอบและสิทธิ์ admin ยังต้องสรุป D03 ไม่ได้ตัดสิทธิ์เจ้าหน้าที่ออก

| สถานะเริ่มต้น              | การกระทำ                       | สถานะถัดไป    | ผู้ทำตามข้อเสนอ                         |
| -------------------------- | ------------------------------ | ------------- | --------------------------------------- |
| ยังไม่มีนัด                | จองรอบที่เปิดและยังไม่เริ่ม    | `pending`     | ผู้ป่วยเจ้าของนัด                       |
| `pending`                  | อนุมัติก่อนรอบเริ่ม            | `confirmed`   | staff/admin                             |
| `pending`                  | ปฏิเสธ                         | `rejected`    | staff/admin                             |
| `pending` หรือ `confirmed` | ยกเลิกก่อนรอบเริ่ม             | `cancelled`   | เจ้าของนัด หรือ staff/admin พร้อมเหตุผล |
| `confirmed` | เริ่มตรวจ | `in_progress` | เจ้าหน้าที่; เสนอให้แพทย์ประจำรอบทำได้ด้วยตาม D03 |
| `in_progress` | เปลี่ยนคิวเป็นตรวจเสร็จ หลังแพทย์บันทึกผล | `completed` | เจ้าหน้าที่; เสนอให้แพทย์ผู้ตรวจทำได้ด้วยตาม D03 |
| `confirmed`                | ยืนยันไม่มา หลังเวลาสิ้นสุดรอบ | `no_show`     | staff/admin                             |

`pending` ที่เลยเวลาเริ่มแล้วยังไม่ได้อนุมัติให้เจ้าหน้าที่ปฏิเสธพร้อมเหตุผลในรุ่นแรก ห้ามอนุมัติย้อนหลังเพื่อสร้างคิวใหม่ สถานะปลายทางไม่มีการย้อนกลับในกระบวนการปกติ ข้อผิดพลาดใช้ขั้นตอนแก้ไขที่บันทึกเหตุผลแยกต่างหากในอนาคต

กติกาของรอบเวลา:

- เวลาเริ่มต้องก่อนเวลาสิ้นสุด ความจุต้องเป็นจำนวนเต็มมากกว่า 0 และรอบของแพทย์เดียวกันต้องไม่ทับซ้อน
- `booked_count` ในข้อเสนอนี้หมายถึงจำนวนที่ใช้ความจุของรอบ ได้แก่ `pending`, `confirmed`, `in_progress`, `completed`, `no_show` ไม่ใช่จำนวนผู้ป่วยที่กำลังรอตรวจ
- `cancelled` และ `rejected` ไม่ใช้ความจุ การเปลี่ยนเป็นสองสถานะนี้คืนจำนวนได้ครั้งเดียว การส่งคำขอซ้ำห้ามคืนซ้ำ
- การตรวจความจุ เพิ่มนัด ออกหมายเลขคิว และเพิ่มจำนวนต้องสำเร็จด้วยกันในธุรกรรมเดียว รองรับหลายคนกดพร้อมกัน
- ผู้ป่วยหนึ่งคนมีนัดที่ใช้ความจุได้ไม่เกินหนึ่งรายการต่อรอบ อนุญาตจองใหม่หลังยกเลิก/ถูกปฏิเสธถ้ารอบยังเปิด
- ห้ามจองรอบที่เริ่มไปแล้ว เต็ม หรือปิด แม้ส่งคำขอตรงโดยไม่ผ่านหน้าจอ
- การยกเลิกต้องไม่เปิดรอบที่เจ้าหน้าที่ปิดไว้ และไม่เปิดจองรอบในอดีต
- ห้ามลดความจุต่ำกว่าจำนวนที่ใช้ไปแล้ว ห้ามเปลี่ยนแพทย์/วัน/เวลาของรอบที่มีนัดโดยเงียบ ๆ
- คิวใช้เลขเรียงภายในรอบที่ออกจากฐานข้อมูล ไม่เปลี่ยนเลขของคนอื่นเมื่อมีการยกเลิก และไม่จำเป็นต้องนำเลขที่ยกเลิกกลับมาใช้

ไม่เพิ่ม unique constraint ที่ `slot_id` เพียงคอลัมน์เดียว เพราะข้อเสนอยังคงรองรับหลายคนต่อรอบ ต้องออกแบบการป้องกันนัดซ้ำให้ตรงกับความจุและสถานะข้างต้น

## 5. ผลตรวจ ใบสั่งยา และการจ่ายยา

- หนึ่งนัดมีบันทึกการตรวจหลักได้หนึ่งรายการ ต้องตรวจให้ `patient_id` และ `doctor_id` ตรงกับนัดและแพทย์ประจำรอบ
- แพทย์บันทึกผลและรายการยาได้เฉพาะนัดที่ตนรับผิดชอบ รายการรอจ่ายของเภสัชกรเกิดจากผลตรวจที่ปิดแล้ว
- ใบสั่งยาต้องมีรหัสรายการที่คงที่ ระบุยา จำนวน หน่วย วิธีใช้ และจำนวนวันที่แพทย์กรอก ไม่ให้ระบบเดาวิธีรักษา
- รายการจ่ายต้องเชื่อมกลับไปยังใบสั่งยาและผู้ป่วยได้ ป้องกันกดยืนยันใบเดิมซ้ำ ไม่ใช้เพียงรหัสยาเป็นตัวระบุว่าจ่ายไปแล้ว
- ข้อเสนอขั้นต่ำคือจ่ายทั้งใบครั้งเดียว ตรวจยาทุกตัวก่อนตัดสต๊อก หากตัวใดไม่พอ ถูกระงับ หรือหมดอายุ ให้ทั้งรายการไม่สำเร็จและแสดงสาเหตุ
- ยืนยันจ่ายแล้วต้องเปลี่ยนยอดยา สถานะจ่าย และบันทึกคลังทุกตัวในธุรกรรมเดียว การกดซ้ำหลังสำเร็จต้องคืนผลเดิมหรือบอกว่าจ่ายแล้ว
- จำนวนที่ขอจ่ายต้องเป็นจำนวนเต็มบวก รับผู้กระทำจากบัญชีที่ตรวจสอบแล้ว ไม่เชื่อ `pharmacist_id` ที่ browser ระบุเอง
- การรับเข้าและปรับยอดต้องผ่านกระบวนการที่สร้างประวัติเช่นกัน ไม่เปิดแก้ `stock` โดยตรงจากฟอร์มข้อมูลยา
- ไฟล์ 03 กำหนด `inventory_logs.quantity` เป็นจำนวนเปลี่ยนแปลงที่มีเครื่องหมายอยู่แล้ว: รับเข้าเป็นบวก จ่าย/ชำรุดเป็นลบ ส่วนกติกาปรับยอดและการเพิ่มยอดก่อน/หลังเป็นรายละเอียดที่เสนอให้สรุปใน D05
- บันทึกคลังเป็นประวัติที่ไม่แก้ทับ หากผิดให้สร้างรายการแก้ไขที่อ้างรายการเดิม
- ไฟล์ 02 ระบุเพิ่ม/แก้/ลบแพทย์และแผนก และระงับยา ข้อเสนอสำหรับรายการที่มีประวัติอ้างอิงคือใช้การระงับหรือเก็บแบบไม่แสดงในรายการใช้งาน โดยต้องตกลงความหมายของปุ่มลบกับทีม ไม่ถือว่าตัดความสามารถลบออกจากขอบเขตเดิม

ฐานจากไฟล์ 03 ใช้ `prescribed_medications` เป็น JSON ใน `medical_records` ให้คงแบบนี้เป็นจุดเริ่มต้น สิ่งที่ยังขาดคือรหัสอ้างอิงรายการจ่าย สถานะจ่าย และการกันจ่ายซ้ำ ซึ่งอาจเติมบนแบบเดิมได้ การแยก `prescription_items` เป็นอีกทางเลือกที่เปลี่ยนฐาน ต้องมีข้อยุติ D05 ก่อน ไม่ถือว่าเป็นข้อบังคับเพื่อให้ทำฟีเจอร์เดิมได้

## 6. เตือนกินยาและงานส่งอีเมล

ใช้รอบตรวจ **ทุก 15 นาที** ตามไฟล์ 04 เป็นฐาน ส่งทั้งอีเมลและแจ้งเตือนในเว็บ ส่วนการเลือกผู้ประมวลผลและผู้ให้บริการจริงยังต้องสรุปใน D06 ถ้าจะลดเป็น 5 นาทีให้บันทึกเป็นการเปลี่ยนฐานแยกต่างหาก

- รอบเตือนระบุยา วันที่เริ่ม วันที่สิ้นสุดถ้ามี และเวลาในแต่ละวันของ `Asia/Bangkok` ห้ามเวลาเดียวกันซ้ำในรอบเดียว และวันที่สิ้นสุดต้องไม่ก่อนวันที่เริ่ม
- หนึ่งมื้อระบุด้วยคู่ `(reminder_id, scheduled_datetime)` และต้องมีได้เพียงรายการเดียวทั้งระดับฐานข้อมูลและคำสั่งบันทึก
- การกด “กินแล้ว” ซ้ำไม่สร้างมื้อใหม่และไม่ทับเวลาที่กินครั้งแรกโดยอัตโนมัติ
- ไฟล์ 03 มี `pending`, `taken`, `missed` อยู่แล้ว และไฟล์ 02 ให้ผู้ป่วยบันทึกกินแล้ว/ยังไม่กิน สิ่งที่รอสรุปใน D07 คือเมื่อไรระบบเปลี่ยนเป็น `missed` และรับบันทึกย้อนหลังอย่างไร ไม่ใช่การตัดสินใจลบสถานะเดิมออก ห้ามนับมื้อในอนาคตเป็นมื้อที่พลาด
- การแก้รอบเตือนมีผลต่อมื้ออนาคตเท่านั้น ไม่เปลี่ยนประวัติมื้อที่เกิดแล้ว การหยุดเตือนต้องหยุดงานอนาคตที่ยังไม่ส่ง
- งานตามเวลาสร้างหรือค้นหามื้อที่ถึงกำหนด บันทึกแจ้งเตือนในเว็บ และจัดงานอีเมล โดยไม่ต้องเปิดหน้าเว็บค้างไว้
- เสนอให้เก็บงานส่งแยกตามมื้อและช่องทาง พร้อมสถานะ จำนวนครั้งที่ลอง เวลาลองครั้งถัดไป เวลาส่งสำเร็จ และข้อผิดพลาดล่าสุด
- ผู้ประมวลผลงานต้องจองงานก่อนส่ง ป้องกันผู้ประมวลผลสองตัวหยิบงานเดียวกัน ใช้รหัสป้องกันคำขอซ้ำของผู้ให้บริการถ้ารองรับ
- หากหมดเวลารอหลังผู้ให้บริการรับอีเมลไปแล้ว อาจไม่ทราบว่าส่งสำเร็จหรือไม่ ต้องมีวิธีสอบทาน/ลองใหม่ ไม่รับรองการส่ง “ครั้งเดียวเสมอ” โดยไม่มีหลักฐานจากผู้ให้บริการ
- อีเมลใช้ข้อความเตือนทั่วไปและลิงก์กลับระบบ ไม่ใส่ผลวินิจฉัยในหัวข้อหรือเนื้อหา ผู้เปิดลิงก์ต้องเข้าสู่ระบบก่อนอ่านข้อมูลส่วนตัว
- แยกผล “ระบบสร้างมื้อแล้ว”, “แจ้งเตือนในเว็บแล้ว” และ “ผู้ให้บริการรับส่งอีเมลแล้ว” ไม่แสดงว่าสำเร็จทั้งหมดเมื่อสำเร็จเพียงขั้นแรก

รอบประมวลผลฐานคือ 15 นาที ผู้ให้บริการ ผู้ดูแลงาน และแบบเก็บสถานะส่งเป็นรายละเอียด D06 ที่ยังต้องสรุป ไม่ได้มีการตั้ง Cron หรือส่งอีเมลจากการจัดทำเอกสารครั้งนี้

รายละเอียดที่ต้องเติมให้ฟีเจอร์เดิมทำงานครบ:

- เลือกว่าจะสร้างมื้อไว้ล่วงหน้าหรือสร้างเมื่อถึงกำหนด โดยหนึ่งมื้อต้องมีตัวระบุเดียวกันทุกครั้งที่งานระบบทำซ้ำ
- เมื่อปิดหรือลบรายการเตือน ต้องยกเลิกงานอนาคตที่ยังไม่เริ่มส่ง และกำหนดว่าจะเก็บประวัติที่เกิดแล้วไว้แบบใด ห้ามปล่อยงานส่งค้างที่หาต้นทางไม่พบ
- เมื่อมีงานกำลังส่ง ให้กำหนดจุดที่การปิดเตือนยังหยุดได้ กับจุดที่ส่งให้ผู้ให้บริการไปแล้วและเรียกคืนไม่ได้ เพื่อเขียนเกณฑ์ทดสอบให้ตรงความจริง
- การสร้างจากใบสั่งยาเป็นทางเลือกที่ไฟล์ 01 กล่าวถึง ยังต้องเชื่อมขอบเขตกับหน้าตั้งเตือนในไฟล์ 02 ก่อนสรุป D14

## 7. วันเวลาและตัวเลขสรุป

| รายการ              | นิยามที่เสนอ                                                                  |
| ------------------- | ----------------------------------------------------------------------------- |
| วันนี้              | วันที่ตาม `Asia/Bangkok` ไม่ตัดวันที่ UTC จาก `toISOString()` โดยตรง          |
| นัดหมายวันนี้       | นัดที่วันของรอบตรงกับวันนี้และไม่ใช่ `cancelled`/`rejected`                   |
| คิวคงเหลือแพทย์     | นัดของแพทย์คนนั้นในวันนี้ที่เป็น `confirmed`/`in_progress` แยกจำนวนแต่ละสถานะ |
| แพทย์ตรวจแล้ววันนี้ | นับนัดของแพทย์คนนั้นที่เป็น `completed` ในวันที่บริการวันนี้; เป็นตัวเลขตาม User Story เดิม |
| ผู้ป่วยแต่ละแผนก | เสนอให้นับผู้ป่วยไม่ซ้ำต่อแผนกในช่วงวันที่บริการที่เลือก โดยไม่รวม cancelled/rejected; ทีมต้องสรุปว่าจะนับผู้ป่วยไม่ซ้ำหรือจำนวนครั้งก่อนใช้จริง |
| ผู้ป่วยทั้งหมด      | จำนวนโปรไฟล์บทบาท `patient` ภายในขอบเขตที่ผู้ดูมีสิทธิ์                       |
| ยาใกล้หมด           | ยาที่เปิดใช้งานและ `stock <= min_stock` นับเป็นจำนวนรายการยา ไม่ใช่จำนวนเม็ด  |
| ยาหมดอายุ           | ยาที่มี `expiry_date` ก่อนวันที่วันนี้ตามคลินิก แยกจากตัวเลขยาใกล้หมด         |
| แจ้งเตือนยังไม่อ่าน | จำนวนข้อความของบัญชีปัจจุบันที่ `is_read = false`                             |

ค่าตัวเลข 0 หมายถึงอ่านข้อมูลสำเร็จแล้วไม่มีรายการเท่านั้น หากคำขอล้มเหลวให้แสดงว่าโหลดไม่ได้ การคำนวณในหน้าแดชบอร์ดและหน้ารายการต้องใช้นิยามเดียวกัน

อัตราไม่มาตามนัดและอัตรากินยาต่อเนื่องยังไม่อยู่ในตัวเลขขั้นต่ำ ห้ามนำจำนวนรายการทั้งหมดมาเป็นตัวหารโดยยังไม่ระบุช่วงเวลาและสถานะที่นับ

## 8. ข้อกำหนดข้อมูลที่ต้องสะท้อนในแบบฐานข้อมูล

นี่คือรายการสำหรับออกแบบ migration ภายหลัง ไม่ใช่ SQL สำหรับรันในตอนนี้

- จำกัดค่าบทบาทและสถานะตามชุดที่ตกลง ไม่พึ่ง TypeScript เพียงอย่างเดียว
- สต๊อกและจุดเตือนไม่ติดลบ ความจุมากกว่า 0 และจำนวนจองอยู่ระหว่าง 0 กับความจุ
- ป้องกันรอบแพทย์ทับซ้อน นัดซ้ำในรอบเดียว และบันทึกการตรวจซ้ำต่อนัด
- ห้ามคู่รอบเตือน/เวลามื้อซ้ำ และห้ามงานแจ้งเตือนช่องทางเดียวของมื้อเดียวซ้ำ
- ตรวจความสัมพันธ์ระหว่างนัด ผู้ป่วย แพทย์ ใบสั่งยา และรายการจ่ายให้ตรงกัน
- เก็บการเปลี่ยนแปลงข้อมูลสำคัญและเวลาปรับปรุงจากฝั่งที่เชื่อถือได้
- จำกัดสิทธิ์อ่านและแก้ทั้งแถวและช่องข้อมูล รวมถึงการเรียกฟังก์ชันฐานข้อมูล

## 9. เกณฑ์ยอมรับสำหรับนำไปสร้างการทดสอบ
