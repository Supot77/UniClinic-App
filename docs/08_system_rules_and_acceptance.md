# 08. กติการะบบและเกณฑ์ตรวจรับ

ปรับปรุง 20 กันยายน 2569 (2026-09-20) — เพิ่มเกณฑ์การแก้ไขและยกเลิกวันลาจากชิปในปฏิทินตาม D26/D28; ยังไม่ใช่หลักฐานว่าโค้ดหรือฐานข้อมูลทำครบแล้ว

## 1. หลักการ scope

- ระบบเป็น manual-first ไม่มี automation, worker, cron, retry, catch-up, email หรือ Web Push
- ระบบไม่เปลี่ยนสถานะจากเวลาเอง ทุกการอนุมัติ ปิด slot จบตรวจ จ่ายยา และบันทึกเตือนต้องมีผู้ใช้ที่มีสิทธิ์กดคำสั่ง
- ใช้ validation พื้นฐานเพื่อป้องกันข้อมูลผิดและข้อมูลซ้ำเท่านั้น ไม่เพิ่มกฎผ่อนผันหรือเส้นตายย่อย
- Runtime ใช้ Supabase จริงผ่าน database repository; automated unit/component tests ใช้ mock และไม่เรียกฐานจริงหรือบริการภายนอก

## 2. สิทธิ์

| บทบาท | งานหลัก | ขอบเขตจำกัด |
| --- | --- | --- |
| patient | โปรไฟล์ จองนัด ดูผลตรวจ/ยา รายการเตือน และ Dashboard ของตน | อ่านหรือแก้ข้อมูลของคนอื่นไม่ได้ และเข้า Dashboard ของ role อื่นไม่ได้ |
| medical | แพทย์ตรวจและบันทึกผล/รายการยา และบันทึก แก้ไข หรือยกเลิกวันลาของตนเอง; เภสัชกรดูประวัติแพ้ยา จัดการยา และค้นหารายชื่อผู้ป่วย | แพทย์แก้เฉพาะนัดและวันลาของตน; ไม่เปิด diagnosis ในส่วนงานคลังยา |
| staff_admin | จัดการ slot นัด วันลา บัญชี รายการเตือน สถิติรวม และ Broadcast ตามสิทธิ์ | Dashboard แสดงข้อมูลรวม ไม่เปิด diagnosis หรือผลตรวจ |

## 3. กติกาการทำงาน

- ทุก role มี guarded entry page/dashboard ของตน เมื่อข้อมูลหรือคำสั่งต่างกันต้องใช้ role-specific page/container/component; shared UI ใช้ร่วมกันได้เมื่อไม่มี permission logic
- UI guard และการซ่อนเมนูไม่ใช่ขอบเขตความปลอดภัยสุดท้าย ทุกคำสั่งต้องตรวจ session/role/ownership ใน service/repository และ Supabase RLS/RPC
- Production UI ห้ามมีตัวเลือกสลับ role เพื่อจำลองสิทธิ์ ผู้ทดสอบต้องเข้าสู่ระบบด้วยบัญชีของ role นั้น

- เจ้าหน้าที่/แอดมิน (`staff_admin`) หรือแพทย์เจ้าของงาน (`medical`) กรอก slot เองทีละรอบ หรือใช้คำสั่ง batch ที่ผู้ใช้กดเองเพื่อสร้าง slot หลายวันตามวันในสัปดาห์ (เฉพาะวันจันทร์ถึงศุกร์) ตรวจไม่ให้เวลาทับกัน อยู่ในเวลาทำการ 08:30–16:30 และไม่ทับพัก 12:00–13:00; ไม่สามารถเพิ่มรอบตรวจของวันในอดีตหรือช่วงเวลาที่ผ่านไปแล้วของวันปัจจุบันตาม `Asia/Bangkok` ได้ โดย batch จะข้ามเฉพาะช่วงที่ผ่านไปแล้วของวันนี้และยังใช้เวลาทำการปกติในวันอนาคต; ปิด slot เองเมื่อจำเป็น; หากรอบตรวจมีคนจองแล้ว ปิดรับเพิ่มได้แต่ห้ามแก้เวลาเริ่ม-สิ้นสุด; รอบที่ปิดด้วยมือแต่ยังไม่ถึงเวลาเริ่ม แก้ไขรายละเอียดได้โดยคงสถานะ `ปิดรอบ` ไว้ และเมื่อเลยเวลาเริ่มแล้วจะแก้ไขไม่ได้
- `staff_admin` บันทึก แก้ไข หรือยกเลิกวันลาให้แพทย์คนใดก็ได้ ส่วน `medical` บันทึก แก้ไข หรือยกเลิกได้เฉพาะของตนเอง; วันลาใหม่ต้องไม่เป็นอดีต วันเริ่มไม่เกินวันสิ้นสุด และไม่ทับช่วงเดิม
- ปฏิทินแสดงชิปวันลา; ผู้มีสิทธิ์คลิกชิปเพื่อเปิด Modal แก้ไขหรือยกเลิก ส่วน `patient` ไม่มีสิทธิ์จัดการหรืออ่านข้อมูลวันลา; การบันทึกใหม่และการแก้ไขแสดงจำนวน slot เดิมที่ได้รับผลกระทบก่อนบันทึก
- การบันทึกหรือยกเลิกวันลาไม่ลบ ปิด หรือเปิด slot และไม่นัดหมายเดิมอัตโนมัติ; เจ้าหน้าที่จัดการ slot/นัดที่ได้รับผลกระทบด้วยมือ
- ผู้ป่วย (`patient`) จอง slot ที่ว่างเป็น `pending`; `staff_admin` หรือ `medical` เจ้าของ slot อนุมัติหรือปฏิเสธด้วยมือ
- `staff_admin` และ `medical` เปลี่ยนสถานะการตรวจด้วยมือ; `medical` จบตรวจได้เมื่อบันทึกผลตรวจแล้ว
- หากปิดรอบหรือแพทย์ปิดใช้งาน `staff_admin` ปิด slot และติดต่อจัดการนัดเดิมทีละรายการ ไม่มีการย้ายหรือยกเลิกอัตโนมัติ
- `medical` จ่ายเต็มตามจำนวนที่สั่งในครั้งเดียว หากยาไม่พอให้ปฏิเสธการจ่ายและบันทึกเหตุผล
- `staff_admin` สร้างรายการเตือนจากยาที่จ่ายเต็ม ผู้ป่วยกดบันทึกผลเองในเว็บ ไม่มีการคำนวณ `missed` หรือการเตือนซ้ำ
- `staff_admin` ส่ง Broadcast เมื่อกดส่งเท่านั้น

## 4. Acceptance Criteria

| รหัส | สถานการณ์ | ผลที่ต้องได้ |
| --- | --- | --- |
| AC01 | สมัครด้วยอีเมลนอกโดเมน | ระบบปฏิเสธและไม่สร้างบัญชี |
| AC02 | ผู้ใช้เปิดข้อมูลของบัญชีอื่น | ระบบปฏิเสธทั้ง UI และ service |
| AC03 | ผู้มีสิทธิ์สร้าง slot เวลาทับกัน ความจุไม่ถูกต้อง เลือกวันในอดีต หรือเลือกเวลาที่ผ่านไปแล้วของวันปัจจุบัน | ไม่บันทึกและแสดงข้อผิดพลาด |
| AC04 | Patient จอง slot เต็มหรือส่งคำขอซ้ำ | ไม่สร้างนัดซ้ำและจำนวนจองไม่เกินความจุ |
| AC05 | `staff_admin` หรือ `medical` เจ้าของ slot อนุมัติ/ปฏิเสธนัด | สถานะเปลี่ยนตามคำสั่งและ role/ownership ที่ถูกต้อง |
| AC06 | `medical` จบตรวจโดยไม่มีผลตรวจ หรือแก้นัดของแพทย์อื่น | ระบบปฏิเสธและข้อมูลเดิมไม่เปลี่ยน |
| AC07 | `staff_admin` จัดการนัดเมื่อปิดรอบหรือปิดใช้งานแพทย์ | เปลี่ยนเฉพาะรายการที่เลือก ไม่มี auto-cancel หรือ auto-reschedule |
| AC08 | `medical` จ่ายยาเมื่อ stock ไม่พอ | ปฏิเสธการจ่าย ไม่ตัด stock และแสดงเหตุผล |
| AC09 | `medical` จ่ายเต็มสำเร็จ | ตัด stock ตามจำนวนจริงและบันทึกผู้ทำกับเวลา |
| AC10 | `staff_admin` สร้างเตือนจากยาที่ยังไม่จ่ายเต็ม | ระบบปฏิเสธการสร้าง |
| AC11 | Patient บันทึกผลเตือนของบัญชีอื่น | ระบบปฏิเสธ |
| AC12 | `staff_admin` ส่ง Broadcast | ข้อความถูกสร้างเมื่อกดส่ง และไม่มีการส่งซ้ำตามเวลา |
| AC13 | คำสั่งใด validation ไม่ผ่าน | state เดิมไม่เปลี่ยน |
| AC14 | เปิดหน้าหลังเวลาผ่านไป | ระบบไม่เปลี่ยนสถานะนัด ยา หรือเตือนเอง |
| AC15 | ระบบทดสอบ | ไม่เรียก network, email provider, worker หรือฐานข้อมูลจริง |
| AC16 | Runtime อ่านหรือเขียนข้อมูลหลัก | ใช้ Supabase database repository และบังคับสิทธิ์ด้วย session + RLS/RPC ไม่มี mock fallback แบบเงียบ |
| AC17 | ผู้ใช้เปิด entry page หรือ flow ของ role อื่น | route/layout guard ปฏิเสธหรือ redirect และ query ฐานข้อมูลไม่คืนข้อมูลเกินสิทธิ์ |
| AC18 | Flow ที่ role มีข้อมูลหรือคำสั่งต่างกัน | render role-specific page/container โดยไม่มี production role switcher และยังใช้ shared presentational component ได้ |
| AC19 | `medical` หรือ `staff_admin` บันทึกวันลาในอนาคตที่ช่วงถูกต้อง | สร้างรายการวันลา แสดงชิปบนปฏิทิน และแสดงช่วงวันลาข้างชื่อแพทย์ |
| AC20 | บันทึกวันลาในอดีต ช่วงกลับด้าน ช่วงทับซ้อน หรือโดย role ที่ไม่มีสิทธิ์ | ระบบปฏิเสธและ state เดิมไม่เปลี่ยน |
| AC21 | สร้าง slot ใหม่ในช่วงวันลา หรือบันทึกวันลาเหนือ slot เดิม | slot ใหม่ถูกปฏิเสธ แต่ slot และนัดเดิมยังคงอยู่ พร้อมจำนวนผลกระทบให้จัดการด้วยมือ |
| AC22 | ผู้มีสิทธิ์ยกเลิกวันลา | ลบเฉพาะรายการวันลา ไม่เปลี่ยนสถานะหรือนัดหมายของ slot เดิม |
| AC23 | ผู้มีสิทธิ์สร้าง slot หลายวันตามช่วงวันที่ วันในสัปดาห์ บริการ และช่วงเวลา | ระบบ preview จำนวนรอบก่อนบันทึก ข้ามช่วงเวลาที่ผ่านไปแล้วเฉพาะวันนี้ ใช้เวลาทำการปกติในวันอนาคต ข้ามวันลา/slot ที่ชนเดิม ไม่แก้ข้อมูลเดิม และตรวจ ownership/RLS ก่อนสร้าง |
| AC24 | ผู้ป่วยจองรอบจนจำนวนจองครบความจุ | ตารางเวลาแสดงสถานะ `เต็ม` และจำนวน `bookedCount/maxCapacity` โดยแยกจาก `ปิดรอบ`; ยกเลิก/ปฏิเสธแล้วคำนวณยอด active ใหม่เมื่อ refresh |
| AC25 | `medical` หรือ `staff_admin` คลิกชิปวันลาที่ตนมีสิทธิ์ในปฏิทิน | เปิด Modal พร้อมข้อมูลเดิม; บันทึกแล้วแก้รายการวันลาเดิม ไม่สร้างรายการซ้ำ; `medical` แก้ได้เฉพาะของตนเองและ `staff_admin` แก้ได้ทุกแพทย์ |
| AC26 | ผู้มีสิทธิ์เลือก `ยกเลิกวันลา` จาก Modal แก้ไข | มี Confirmation; สำเร็จแล้วลบเฉพาะรายการวันลา แสดงผลสำเร็จ และไม่เปลี่ยนสถานะหรือนัดหมายของ slot เดิม; หากไม่ผ่าน state เดิมไม่เปลี่ยน |
| AC27 | ผู้มีสิทธิ์เปิดปฏิทินหรือฟอร์มสร้าง slot ในวันเสาร์-อาทิตย์ | ไม่แสดงปุ่มเพิ่มรอบใน day/week/month และไม่บันทึก slot ใหม่แม้พยายามส่งผ่านฟอร์ม |

## 5. เส้นทางสาธิตขั้นต่ำ

1. ผู้ป่วยสมัครและเข้าสู่ระบบ
2. `staff_admin` สร้าง slot และผู้ป่วยจอง
3. `staff_admin` อนุมัตินัด และ `medical` บันทึกผลตรวจ
4. `medical` จ่ายยาเต็ม และ `staff_admin` กรอกรายการเตือน
5. ผู้ป่วยเปิดรายการของตนและกดบันทึกผลด้วยมือ
6. `staff_admin` ส่ง Broadcast ด้วยมือ
7. `staff_admin` หรือ `medical` บันทึก แก้ไข หรือยกเลิกวันลาจากปฏิทิน ตรวจผลกระทบ และจัดการ slot/นัดเดิมด้วยมือ

ไม่มี SCN สำหรับเลื่อนนัดอัตโนมัติ แบ่งจ่าย/กันยา ยาค้าง email worker missed หรือการเตือนซ้ำ

## 6. เกณฑ์ส่งมอบ

ต้องตรวจ lint, typecheck, test และ build ตามคำสั่งใน README ตรวจ flow หลักด้วย Chrome ที่ 360px และ 1280px รวม keyboard, loading, empty และ error และตรวจ database integration/RLS กับฐาน development หรือ staging ที่ระบุชัดก่อนอ้างว่าเชื่อมฐานจริงผ่าน รายงานผลจริง ไม่ถือว่าเอกสารเป็นหลักฐานว่าระบบผ่านการตรวจรับแล้ว

## วิธีใช้ Acceptance Criteria

แต่ละ AC ต้องตรวจทั้งผลที่ผู้ใช้เห็นและ state หลังคำสั่ง: ระบุบัญชีหรือ role ที่ใช้, ข้อมูลตั้งต้น, คำสั่งที่ทำ, ผลลัพธ์ที่แสดง และข้อมูลที่ยังคงเดิมเมื่อคำสั่งถูกปฏิเสธ กรณีสำเร็จต้องตรวจความสัมพันธ์ของข้อมูลที่เปลี่ยนด้วย เช่น จำนวนจอง, ผลตรวจ, stock หรือ notification ที่เกิดขึ้น

AC01–AC05 ตรวจสมาชิก ตาราง และการตัดสินนัด; AC06–AC09 ตรวจสิทธิ์การตรวจและการจ่ายยา; AC10–AC12 ตรวจรายการเตือนและ Broadcast; AC13–AC15 ตรวจความสมบูรณ์ของ state, การไม่เปลี่ยนตามเวลา และการแยก test จากบริการภายนอก; AC16–AC18 ตรวจ database runtime, RLS และ UI แยกตาม role; AC19–AC22 ตรวจวันลา การกัน slot และการคงข้อมูลเดิม; AC23 ตรวจ batch slot และการ preview ก่อนบันทึก; AC24 ตรวจยอดจองจริงและสถานะเต็มในตารางเวลา; AC25–AC26 ตรวจการแก้ไขและยกเลิกวันลาจากปฏิทินตาม ownership; AC27 ตรวจการซ่อนและปฏิเสธการสร้าง slot ในวันหยุดสุดสัปดาห์

## หลักฐานขั้นต่ำของกรณีไม่ผ่าน

เมื่อ validation หรือ permission ไม่ผ่าน ต้องบันทึก error ที่ระบุสาเหตุได้ และยืนยันค่าที่สำคัญก่อนกับหลังเท่ากัน เช่น สถานะนัด, จำนวนจอง, stock, รายการเตือน หรือกล่องข้อความ กรณีเปิดหน้าหลังเวลาผ่านไปต้องยืนยันด้วยว่าสถานะยังเปลี่ยนได้เฉพาะจากคำสั่งที่มีสิทธิ์
