# 07. พื้นฐานโครงการ ขอบเขตเดิม และรายละเอียดที่ต้องเติม

วันที่: 2 กันยายน 2569 (2026-09-02)  
สถานะ: ทบทวนให้ตรงกับฐาน 01–06 พร้อมแยกข้อเสนอเพิ่มเติม — ยังไม่ได้เปลี่ยนโค้ดหรือฐานข้อมูล

## 1. เป้าหมายร่วมกัน

พัฒนาเว็บสำหรับสาธิตการทำงานของคลินิกมหาวิทยาลัย ตั้งแต่ผู้ป่วยสมัครสมาชิกและจองคิว เจ้าหน้าที่จัดคิว แพทย์บันทึกการตรวจ เภสัชกรจ่ายยา จนถึงผู้ป่วยตั้งเตือนและบันทึกการกินยา โดยแต่ละบทบาทเข้าถึงข้อมูลตามหน้าที่

เกณฑ์ความสำเร็จหลักคือทีมสาธิตกระบวนการนี้ด้วยข้อมูลทดสอบได้ครบและข้อมูลสอดคล้องกัน ไม่ใช่เพียงเปิดหน้าจอของแต่ละส่วนได้ ขอบเขตนี้เป็นมินิโปรเจกต์รายวิชา ไม่ได้อ้างว่าผ่านการรับรองให้เป็นระบบเวชระเบียนสำหรับใช้งานจริง

กำหนดนำเสนออ้างอิงเอกสารเดิม: 18 กันยายน 2569 หากกำหนดเปลี่ยน ให้แก้วันที่ในเอกสารแผนงานก่อนปรับลำดับส่งมอบ

## 2. สิ่งที่มีอยู่กับสิ่งที่ต้องพัฒนา

| ส่วน | สิ่งที่พบ ณ วันที่ตรวจ | สิ่งที่ยังต้องทำในระยะพัฒนา |
| --- | --- | --- |
| โครงสร้าง | แบ่งหน้า ส่วนประกอบ บริการ และชนิดข้อมูลไว้แล้ว | ใช้รูปแบบชื่อและข้อตกลงร่วมกัน |
| หน้าจอ | มีหน้าแรก แบบฟอร์มสมาชิก และหน้าโครงของแต่ละงาน | เชื่อมข้อมูลจริง ตรวจข้อมูล และจัดการ loading/error |
| ฐานข้อมูล | มี migrations สร้าง 11 ตารางพร้อม RLS | ทบทวนสิทธิ์ ข้อกำหนดข้อมูล และธุรกรรมสำคัญ |

| การเตือน | มีบริการจัดการรอบเตือนและประวัติ | เพิ่มงานประมวลผลตามเวลา การส่งอีเมล และการลองใหม่ |
| การทดสอบ | มีไฟล์ตั้งค่าเครื่องมือ | จัดสภาพแวดล้อมและสร้างกรณีทดสอบที่ตรวจผลได้จริง |

## 3. บทบาทตามฐานเดิม

ไฟล์ 02 และ 03 ระบุ 5 บทบาทไว้แล้ว แบบข้อมูลมีช่อง `role` หนึ่งค่าต่อโปรไฟล์ จึงใช้เป็นฐานการออกแบบ หากต้องการหลายบทบาทต่อบัญชีเป็นข้อเสนอเปลี่ยนแบบ ไม่ใช่เงื่อนไขที่เอกสารเดิมกำหนดไว้

| บทบาทในระบบ | ผู้ใช้งาน | ความรับผิดชอบหลัก |
| --- | --- | --- |
| `patient` | นักศึกษาหรือบุคลากรที่เข้ารับบริการ | ข้อมูลตนเอง การนัดหมาย การเตือน และประวัติของตน |
| `staff` | เจ้าหน้าที่คลินิก | แผนก ตารางแพทย์ อนุมัตินัด และคิวหน้างาน |
| `doctor` | แพทย์ | คิวที่รับผิดชอบ บันทึกการตรวจ และสั่งยา |
| `pharmacist` | เภสัชกร | รายการรอจ่ายยา คลังยา และประวัติการปรับยอด |
| `admin` | ผู้ดูแลระบบ | จัดการบัญชี บทบาท และข้อมูลตั้งต้น |

คำว่า `student` เป็นประเภทผู้รับบริการหรือข้อมูลประจำตัว ไม่ใช่ชื่อบทบาทอีกชุดหนึ่ง บัญชีสมัครทั่วไปเริ่มเป็น `patient` เสมอ ผู้ใช้เลือกสิทธิ์เจ้าหน้าที่เองไม่ได้

การเปิดหน้าจอ การแสดงเมนู และการอนุญาตอ่านหรือแก้ข้อมูลเป็นคนละส่วน ต้องกำหนดให้ตรงกันตามเอกสาร 08

## 4. ขอบเขตงานตาม 01–06 ที่ต้องคงไว้

ตารางนี้คืนความต้องการจากไฟล์ 02 ให้ครบ ไม่ได้ตัดฟีเจอร์ออกเพราะหน้าจอยังไม่เสร็จ การยืนยันอีเมลเป็นรายละเอียดการตั้งค่าสมาชิกที่รอสรุป ส่วนการสมัคร/ล็อกอินด้วย Email/Password และรีเซ็ตรหัสผ่านเป็นฐานเดิม

| หมวด | ต้องสาธิตได้ | ผู้รับผิดชอบตามเอกสารเดิม |
| --- | --- | --- |
| สมาชิกและสิทธิ์ | สมัคร/เข้าสู่ระบบด้วย Email/Password รีเซ็ตรหัสผ่าน แก้โปรไฟล์/ประวัติสุขภาพ เจ้าหน้าที่ค้นหาผู้ป่วยด้วยรหัสหรือเบอร์โทร และผู้ดูแลสร้าง/แก้บัญชี/กำหนดบทบาท | ฟีม |
| แผนกและตาราง | เพิ่ม/แก้/ลบแผนกและแพทย์ ระบุสังกัด สร้างรอบพร้อมความจุ และดูภาพรวมในรูปแบบปฏิทิน | ช้อป |
| นัดหมายและการตรวจ | ดูเวลาว่าง จอง ยกเลิกล่วงหน้า เจ้าหน้าที่อนุมัติ/ปฏิเสธและเปลี่ยนสถานะคิว แพทย์ดูคิวตนตามเวลาและบันทึกผลตรวจ/คำแนะนำ/รายการยา | ปาย |
| คลังยา | เพิ่ม/แก้/ระงับยา ดูสต๊อกและวันหมดอายุ ดูรายการแพทย์สั่ง ยืนยันจ่ายเพื่อตัดสต๊อก ประวัติรับเข้า/จ่าย/ปรับยอด และให้แพทย์อ่านสต๊อกก่อนสั่ง | กัญจน์ |
| เตือนกินยา | สร้าง/แก้ยาและเวลาที่เตือน วันเริ่ม/สิ้นสุด บันทึกกินแล้ว/ยังไม่กิน ดูประวัติ ปิดหรือลบรายการเตือน และส่งอีเมลอัตโนมัติ | กลอง |
| แจ้งเตือนและสถิติ | กล่องแจ้งเตือนนัด/ยา อ่านแล้ว/ลบ เจ้าหน้าที่ส่ง Broadcast ไปยังกลุ่มเป้าหมาย สถิติภาพรวม/ผู้ป่วยแต่ละแผนก/ยาใกล้หมด และสรุปตรวจแล้ว/คิวเหลือของแพทย์แต่ละคน | เฮิร์บ |

การเตรียมบัญชีสาธิตล่วงหน้าช่วยทดสอบได้ แต่ไม่ถือว่าทดแทนความสามารถสร้าง/แก้ผู้ใช้และกำหนดบทบาทของผู้ดูแลตาม User Story หากจะใช้ขั้นตอนผ่านเครื่องมือผู้ดูแลแทนหน้าจอในเว็บ ต้องระบุรูปแบบส่งมอบและให้ทีมตรวจเทียบเกณฑ์รายวิชาก่อน

## 5. แยกขอบเขตเดิมออกจากข้อเสนอเพิ่มหรือลดงาน

| รายการ | ฐานเดิมและสถานะของข้อเสนอ |
| --- | --- |
| ปฏิทินและการลากวาง | ปฏิทินเป็นฐานเดิม ต้องคงไว้; การลากวางไม่ได้ระบุเป็นข้อบังคับ จึงไม่จำเป็นต้องเพิ่มเพื่อให้ผ่านความต้องการเดิม |
| เปลี่ยนนัดในขั้นตอนเดียว | เอกสารเดิมมีจองและยกเลิก ไม่ได้ระบุการย้ายคิวในคำสั่งเดียว เป็นความสามารถเพิ่มหากทีมเลือกทำ |
| ตั้งเตือนจากใบสั่งยา | ไฟล์ 01 กล่าวถึงเป็นทางเลือก ส่วน 02 เน้นผู้ป่วยตั้งเอง ต้องสรุปความเชื่อมโยงก่อนเพิ่มหรือระบุว่าไม่ทำ |
| Broadcast และลบแจ้งเตือน | ทั้งสองเป็นฐานเดิม ข้อเสนอให้เลื่อนยังไม่มีข้อยุติ จึงคงในขอบเขตและแผนงาน |
| กราฟและสถิติ | คงแดชบอร์ดภาพรวม สถิติแผนกและคิวแพทย์ตามเดิม; กราฟขั้นสูงหรืออัตรากินยาต่อเนื่องที่ไม่ได้ระบุชัดเป็นงานเพิ่มเติม |
| Realtime ทุกหน้าจอ | ไม่ได้ระบุเป็นข้อบังคับทุกหน้า วิธีรีเฟรชข้อมูลเป็นรายละเอียดการออกแบบ ไม่ใช้แทนการตรวจความถูกต้องในฐานข้อมูล |
| จัดการบัญชี | คงความสามารถผู้ดูแลตามไฟล์ 02; การลดเหลือบัญชีเตรียมไว้ล่วงหน้าเป็นข้อเสนอเปลี่ยนรูปแบบส่งมอบที่ยังไม่ตกลง |

ไม่รวมในข้อเสนอรุ่นแรก: การจ่ายเงิน ประกันสุขภาพ วิดีโอพบแพทย์ การเชื่อมโรงพยาบาลภายนอก และระบบจัดซื้อหลายคลัง เพราะไม่ได้เป็นเส้นทางหลักของงานที่กำหนดไว้

## 6. ฐานแบบข้อมูลและรายละเอียดรอสรุป

- **ฐานเดิมจาก 03:** 11 ตาราง แพทย์มีช่องสังกัดแผนกหนึ่งค่า รอบมี `max_capacity` และ `booked_count` จึงรับหลายคนได้
- **ฐานเดิมจาก 03:** ER ระบุหนึ่งนัดต่อหนึ่งบันทึกการตรวจ รายการยาหลายรายการเก็บเป็น JSON ใน `medical_records.prescribed_medications`
- **ฐานเดิมจาก 03:** ยามียอดรวมและวันหมดอายุหนึ่งค่าต่อรายการ ประวัติคลังใช้จำนวนเปลี่ยนแปลงที่มีเครื่องหมาย และมื้อยามี `pending`, `taken`, `missed`
- **ฐานเดิมจาก 04:** งานระบบตรวจรอบเตือนทุก **15 นาที** แล้วส่งอีเมลและสร้างแจ้งเตือนในเว็บ ไม่ได้รับรองเวลาเข้ากล่องอีเมลแบบตรงนาที การเปลี่ยนเป็น 5 นาทีเป็นข้อเสนอที่ยังไม่ใช้แทนฐานเดิม
- **รายละเอียดรอสรุป:** การกันที่ของ `pending`, เวลายกเลิก, สิทธิ์เปลี่ยนสถานะแต่ละขั้น และการจัดการนัดค้าง
- **รายละเอียดรอสรุป:** การจ่ายครบใบหรือแบ่งจ่าย สถานะจ่าย และวิธีแก้ใบสั่งเมื่อยาไม่พอ ข้อเสนอจ่ายครบใบครั้งเดียวยังไม่ใช่ข้อยุติ
- **รายละเอียดรอสรุป:** เวลาเปลี่ยนเป็น `missed`, เวลาสร้างมื้อ และการป้องกันแจ้งเตือนซ้ำ
- **รายละเอียดรอสรุป:** ใช้ `Asia/Bangkok` เป็นข้อเสนอเขตเวลากลาง ส่วนข้อมูลสมมติสำหรับสาธิตมีอยู่ในแผน 06 แล้ว

การเพิ่มหลายล็อต แยกตารางใบสั่ง หรือเพิ่มตารางงานส่งอีเมลเป็นข้อเสนอเปลี่ยนแบบข้อมูล ต้องระบุเหตุผลและผลกระทบตาม D04–D06 ก่อนเปลี่ยนจำนวนตารางหรือโครงสร้างเดิม

## 7. แนวทางสถาปัตยกรรมและโฟลเดอร์

คง Next.js, TypeScript, Tailwind CSS และ Supabase ตามโปรเจกต์ที่มีอยู่ ไม่มีข้อเสนอให้เปลี่ยน framework หรือแยก backend ใหม่ทั้งหมด

| ส่วน | ขอบเขตหน้าที่ที่เสนอ |
| --- | --- |
| `src/app` | เส้นทาง หน้า และ layout แบ่งตามงาน ไม่ตั้งเส้นทางตามชื่อสมาชิก |
| `src/components` | ส่วนหน้าจอที่ใช้ซ้ำ แยกส่วนกลางกับส่วนแต่ละฟีเจอร์ |
| `src/services` | จุดเรียกข้อมูลและคำสั่งของระบบ แยก notification ออกจาก dashboard เมื่อพัฒนา |
| `src/hooks` และ `src/context` | สถานะหน้าจอและสถานะสมาชิก ไม่เป็นด่านควบคุมสิทธิ์เพียงจุดเดียว |
| `src/lib` | การเชื่อมต่อและเครื่องมือส่วนกลาง มี client สำหรับแต่ละสภาพแวดล้อมอย่างชัดเจน |
| `src/types` | ชนิดข้อมูลที่สอดคล้องกับฐานข้อมูล แยกข้อมูลแถวเต็มจากข้อมูลบางช่องที่ใช้แสดงผล |
| `supabase/migrations` | การเปลี่ยนฐานข้อมูลที่ทำซ้ำและตรวจสอบลำดับได้ในอนาคต |
| `tests` และ `supabase/tests` | พื้นที่ทดสอบโปรแกรมและสิทธิ์/กติกาฐานข้อมูลที่เสนอให้เพิ่มภายหลัง |
| `docs` | ขอบเขต ข้อตกลง เหตุผลการตัดสินใจ และเกณฑ์ตรวจรับ |

CRUD ทั่วไปใช้ Supabase ที่มีสิทธิ์ข้อมูลเหมาะสมได้ ส่วนจองคิว ยกเลิกคิว และจ่ายยาต้องมีการตรวจและเปลี่ยนข้อมูลในธุรกรรมฐานข้อมูลเดียว งานส่งอีเมลทำจากฝั่งระบบที่เก็บความลับได้

ใช้แบบ 11 ตารางจากไฟล์ 03 เป็นฐานก่อน ข้อกำหนดป้องกันรายการซ้ำและติดตามการจ่ายเป็นสิ่งที่ต้องเติม ส่วนวิธีเก็บยังต้องเลือก ไม่ถือว่าต้องแยกตารางใหม่โดยอัตโนมัติ หากจำเป็นต้องเพิ่มตารางต้องมีข้อยุติและปรับ ER/Data Dictionary ก่อนสร้าง migration

## 8. สิ่งที่นับว่าพื้นฐานพร้อม

- ทีมใช้ชื่อบทบาท สถานะนัด และความหมายของจำนวนยาเหมือนกัน
- มีข้อยุติของรายการที่กระทบข้ามฟีเจอร์ในเอกสาร 09
