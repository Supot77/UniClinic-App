# 02. Requirements และ User Stories

ปรับปรุง 20 กันยายน 2569 (2026-09-20) — เพิ่ม interaction แก้ไข/ยกเลิกวันลาจากปฏิทินตาม D28 และผล reverse-engineer ล่าสุด; ยังไม่ใช่หลักฐานว่า migration ถูก deploy หรือระบบผ่านการตรวจรับแล้ว

Owner trace ล่าสุดอยู่ที่ [docs/owners](owners/README.md); ใช้ตาราง as-built ด้านล่างเพื่ออธิบาย behavior จาก code และไม่ใช้ story target แทนหลักฐาน runtime

## บทบาทที่ใช้ในทุกโมดูล

- ผู้ป่วย (`patient`)
- แพทย์/เภสัชกร (`medical`)
- เจ้าหน้าที่/แอดมิน (`staff_admin`)

แพทย์และเภสัชกรเป็นหน้าที่ภายใต้ `medical` เดียวกัน เจ้าหน้าที่และแอดมินเป็นหน้าที่ภายใต้ `staff_admin` เดียวกัน

ทุก role ต้องเข้าสู่ entry page/dashboard ของตนผ่าน session จริง Flow ที่ข้อมูล คำสั่ง หรือ permission ต่างกันต้องใช้ role-specific page/container/component และไม่มีตัวเลือกสลับ role ใน production UI

## สถานะจากการ reverse-engineer (as-built)

ส่วนนี้บอกสิ่งที่พบในโค้ดปัจจุบัน แยกจาก user story เป้าหมายด้านล่าง:

- นัดหมายที่ route `/appointments` ใช้ PAI runtime และ Supabase RPC (`pai_workspace`, `pai_book_appointment`, `pai_transition_appointment`, `pai_save_record`) เมื่อมี session จริง; ไม่พบการเลื่อนนัดใน route นี้
- ตาราง schedule รองรับ `service → daily offering → slot` และการกรองตามบริการ/แพทย์/วัน แต่ `SchedulingProvider` ยังมี mock composition และบางคำสั่ง weekly schedule ใช้ mock จึงยังสรุปว่า database runtime ครบไม่ได้
- `appointments`/`medical_records` เดิมเป็น schema legacy; runtime ปัจจุบันรวมอยู่ใน `appointments.tsx`, `medical-records.tsx` และ `clinic-care.tsx`
- หน้า pharmacy เป็นเส้นทางแยกที่อ่าน Supabase ตรงและมี mock/local-storage fallback; PAI บันทึกเฉพาะรายการยาที่สั่งในผลตรวจ ยังไม่ใช่หลักฐานว่า dispense เชื่อมกับนัดแบบ end-to-end
- หน้า reminders รองรับ CRUD, pause/resume และ medication log ผ่าน service พร้อม fallback mock บางกรณี ซึ่งเกิน/ไม่ตรงกับ target manual ที่ตัด pause และ automation ออก
- Dashboard ใช้ mock dashboard repository สำหรับ metric บางส่วน ส่วน notifications/Broadcast ใช้ Supabase service/RPC; ต้องแยกผลตรวจจาก runtime จริงเมื่อทดสอบ deployment

## ฟีม — สมาชิกและโปรไฟล์

- ผู้ป่วยนักศึกษา/บุคลากรสมัครด้วยอีเมล @mail.wu.ac.th และรหัสผ่าน ยืนยันอีเมล เข้าสู่ระบบ ออกจากระบบ และรีเซ็ตรหัสผ่านได้
- ผู้ป่วยกรอกข้อมูลบังคับตามประเภท แก้ข้อมูลส่วนตัวและประวัติสุขภาพ มี/ไม่มี/ไม่ทราบได้ โดยไม่เปลี่ยน role เอง
- เจ้าหน้าที่/แอดมินค้นหาผู้ป่วยด้วยรหัสหรือเบอร์โทร เห็นเฉพาะข้อมูลที่อนุญาต
- เจ้าหน้าที่/แอดมินสร้างและจัดการบัญชีคลินิก กำหนดสิทธิ์/ระงับบัญชีแล้ว session เดิมหมดสิทธิ์ทันที

## ช้อป — แผนกและตาราง

### บทบาทเจ้าหน้าที่ / แอดมิน (`staff_admin`)
- ในฐานะเจ้าหน้าที่ ฉันต้องการเพิ่ม แก้ไข และปิดใช้งานหรือลบข้อมูล "แผนก" เพื่อที่จะจัดหมวดหมู่และระบุความถนัดของแพทย์ในคลินิก (โดยแผนกที่มีแพทย์หรือประวัติอ้างอิงจะใช้วิธีปิดใช้งานเพื่อไม่ให้กระทบข้อมูลเดิม)
- ในฐานะเจ้าหน้าที่ ฉันต้องการเพิ่ม แก้ไข และปิดใช้งานข้อมูล "แพทย์" พร้อมผูกบัญชีผู้ใช้ เพื่อที่จะให้ข้อมูลแพทย์และสถานะการออกตรวจเป็นปัจจุบันเสมอ (โดยหากปิดใช้งานแพทย์ ระบบจะคงรอบเดิมไว้และแจ้งเตือนให้ตรวจสอบ)
- ในฐานะเจ้าหน้าที่ ฉันต้องการดูภาพรวมตารางเวลาของแพทย์ทุกคนในรูปแบบปฏิทิน (รายวัน รายสัปดาห์ รายเดือน) พร้อมตัวกรอง เพื่อที่จะตรวจสอบคิวและบริหารจัดการตารางตรวจได้อย่างมีประสิทธิภาพ
- ในฐานะเจ้าหน้าที่ ฉันต้องการสร้างตารางเวลาออกตรวจ (Slot) ของแพทย์ เพื่อที่จะเปิดช่วงเวลาให้ผู้ป่วยทำการจองคิวตรวจรักษา (โดยเป็นไปตามเวลาทำการ จ.–ศ. 08:30–16:30 น. เว้นพักเที่ยง และตรวจไม่ให้เวลาทับซ้อน)
- ในฐานะเจ้าหน้าที่ ฉันต้องการสร้างตารางเวลาแบบทำซ้ำรายสัปดาห์ เพื่อที่จะลดภาระการกรอกข้อมูลทีละวัน
- ในฐานะเจ้าหน้าที่ ฉันต้องการแก้ไข หรือปิดช่วงเวลาออกตรวจที่ยังไม่มีการจอง เพื่อที่จะปรับตารางให้ตรงกับความพร้อมของแพทย์ (โดยระบบต้องล็อกไม่ให้ลบหรือแก้ไขเวลาตรวจที่มีผู้ป่วยจองแล้ว แต่สามารถปิดรับผู้ป่วยเพิ่มได้)
- ในฐานะเจ้าหน้าที่ ฉันต้องการตั้งค่าวันหยุด หรือระบุวันลาของแพทย์ และคลิกแก้ไขหรือยกเลิกวันลาจากปฏิทินได้ เพื่อที่จะปิดกั้นไม่ให้เกิดสล็อตว่างให้ผู้ป่วยจองในวันนั้นและแก้ไขข้อมูลได้รวดเร็ว
- ในฐานะเจ้าหน้าที่ ฉันต้องการเพิ่ม แก้ไข และเปิด/ปิดบริการการรักษา (Service Catalog) เพื่อที่จะกำหนดประเภทบริการที่แพทย์เปิดให้บริการในคลินิก

### บทบาทแพทย์ (`medical`)
- ในฐานะแพทย์ ฉันต้องการดูตารางเวลาออกตรวจของตนเองเป็นค่าเริ่มต้น และสามารถเลือกดูตารางของแพทย์ท่านอื่นแบบดูได้อย่างเดียว เพื่อที่จะวางแผนการทำงานและประสานงานกับทีมได้อย่างสะดวก
- ในฐานะแพทย์ ฉันต้องการสร้างรอบเวลาออกตรวจและเปิดบริการของตนเองได้ เพื่อที่จะกำหนดช่วงเวลาที่ตนเองพร้อมให้บริการตรวจรักษา
- ในฐานะแพทย์ ฉันต้องการแก้ไขหรือปิดรอบตรวจของตนเอง (โดยหากมีผู้ป่วยจองแล้ว สามารถปิดรับเพิ่มได้แต่ห้ามเปลี่ยนเวลาตรวจ และห้ามแก้ไขรอบของแพทย์ท่านอื่น) เพื่อที่จะบริหารจัดการเวลาตรวจของตนเองได้อย่างถูกต้อง
- ในฐานะแพทย์ ฉันต้องการเพิ่มบริการที่ตนเองเชี่ยวชาญได้โดยตรง เพื่อที่จะนำมาใช้เปิดรอบตรวจรักษาผู้ป่วยได้ทันที
- ในฐานะแพทย์ ฉันต้องการบันทึก แก้ไข และยกเลิกวันลาของตนเองจากชิปวันลาในปฏิทิน พร้อมเห็นจำนวนรอบตรวจเดิมที่ได้รับผลกระทบ เพื่อให้ทีมประสานผู้ป่วยและจัดการรอบตรวจด้วยมือได้ทันเวลา

### บทบาทผู้ป่วย (`patient`)
- ในฐานะผู้ป่วย ฉันต้องการดูตารางเวลาออกตรวจของแพทย์ในรูปแบบปฏิทิน พร้อมกรองตามแพทย์ วันที่ และประเภทบริการ เพื่อที่จะค้นหาและเลือกช่วงเวลาตรวจที่สะดวกได้ล่วงหน้า
- ในฐานะผู้ป่วย ฉันต้องการคลิกเลือกช่วงเวลาตรวจที่ว่าง (สถานะ Available) จากหน้าตารางตรวจ เพื่อที่จะส่งต่อไปยังหน้าจองนัดหมายและดำเนินการจองคิวได้สะดวกรวดเร็ว

## ปาย — นัดและผลตรวจ

- ผู้ป่วยดูเวลาว่าง จอง slot และดูสถานะ/ประวัติของตน
- เจ้าหน้าที่/แอดมินอนุมัติ/ปฏิเสธและจัดการนัดที่ได้รับผลกระทบด้วยมือ; `staff_admin` และ `medical` จัดสถานะตรวจ โดยหน้าที่แพทย์ทำเฉพาะนัดตน
- `medical` ในหน้าที่แพทย์อ่านประวัติการรักษาของผู้ป่วยที่รับผิดชอบ; `medical` ในหน้าที่เภสัชกรจัดการยา; ผู้ป่วยอ่านผลหลังจบตรวจ

## กัญจน์ — คลังและการจ่าย

- `medical` ในหน้าที่เภสัชกรเพิ่ม/แก้/ระงับยา รับเข้า/ปรับยอด ดูวันหมดอายุและประวัติคลัง; `medical` ในหน้าที่แพทย์อ่านสต๊อกได้แต่ไม่แก้ยอด (เป็น target story; เส้นทาง pharmacy ปัจจุบันยังมี mock/local-storage fallback)
- `medical` ในหน้าที่เภสัชกรดูชื่อ ประวัติแพ้ยา ใบสั่งและประวัติจ่าย โดยไม่เห็นวินิจฉัย
- `medical` ตรวจ stock และจ่ายเต็มตามจำนวนที่สั่งในครั้งเดียว
- หากยาไม่พอ `medical` ปฏิเสธการจ่ายและบันทึกเหตุผล ไม่มีแบ่งจ่าย กันยา หรือยาค้าง

## กลอง — เตือนและประวัติมื้อ

- เจ้าหน้าที่/แอดมินกรอกรายการเตือนจากยาที่จ่ายเต็ม ผู้ป่วยกดบันทึกผลด้วยตนเอง (target story; code ปัจจุบันยังมี pause/resume และ fallback ที่ต้องปิดหรือยืนยันตาม D22)
- ไม่มี email, worker, missed, การเตือนซ้ำ, การพักเตือน หรือเส้นตายย้อนหลัง

## เฮิร์บ — ข้อความและ Dashboard

- เฉพาะเจ้าหน้าที่/แอดมินกรอกและส่ง Broadcast ด้วยมือไปยังทุกคนหรือ role ที่เลือก
- Dashboard แสดงข้อมูลที่บันทึกแล้วตาม role ไม่คำนวณงานตามเวลาเอง

| บทบาท | Dashboard |
| --- | --- |
| เจ้าหน้าที่/แอดมิน | นัดวันนี้ คิวคงเหลือ ภาระแต่ละแผนก บัญชี และสถิติรวมที่ไม่เปิดข้อมูลผู้ป่วย |
| แพทย์/เภสัชกร | คิวของตนเมื่อเป็นแพทย์ รายการจ่าย และสต๊อกปัจจุบัน |
| ผู้ป่วย | ไม่มีสิทธิ์เข้าหน้า Dashboard; ใช้หน้านัด ยา การเตือน และกล่องข้อความของตนโดยตรง |

ทุกงานใช้สิทธิ์ตาม [08](08_system_rules_and_acceptance.md) ตรวจที่ฝั่งข้อมูลด้วย ไม่อาศัยซ่อนเมนูเพียงอย่างเดียว กติกาที่ยังไม่ครบติดตามใน [10](10_team_decisions.md)

## วิธีตีความ User Story ในเอกสารนี้

รายการด้านบนอธิบาย “ใครทำอะไรกับข้อมูลใด” ไม่ได้แปลว่าทุกหน้าต้องมี workflow แยกใหม่ หากเป็นงานของ `medical` ให้ดูหน้าที่ที่กำลังทำว่าเป็นงานแพทย์หรืองานเภสัชกร แล้วตรวจความสัมพันธ์กับนัด ผู้ป่วย และรายการยาให้ครบ ส่วน `staff_admin` รวมงานเจ้าหน้าที่กับแอดมินไว้ในบัญชีเดียว แต่ยังต้องตรวจสิทธิ์ก่อนทุกคำสั่ง

ผลลัพธ์ของทุก story มีหลักเดียวกัน: ถ้าข้อมูลและสิทธิ์ถูกต้องจึงบันทึกและแสดงผลสำเร็จ; ถ้า validation หรือ permission ไม่ผ่านต้องแสดงเหตุผลและคงข้อมูลเดิม การเปิดหน้าได้หรือการซ่อนเมนูจึงไม่ถือว่า story สำเร็จจนกว่าจะตรวจ service/data layer ด้วย

## แผนที่ผลลัพธ์ตามโมดูล

| โมดูล | ข้อมูลตั้งต้น | ผู้ทำหลัก | ผลลัพธ์ที่ตรวจได้ |
| --- | --- | --- | --- |
| สมาชิก/โปรไฟล์ | อีเมล บัญชี และข้อมูลผู้ป่วย | ฟีม | session, role และโปรไฟล์ตามประเภท |
| แผนก/ตาราง | แผนก แพทย์ วันเวลา และความจุ | ช้อป | slot ที่ไม่ทับกันและสถานะที่ผู้ใช้บันทึก |
| นัด/ผลตรวจ | slot ผู้ป่วย และผู้รับผิดชอบ | ปาย | สถานะนัด ผลตรวจ และรายการยาที่อ้างอิงกัน |
| คลัง/การจ่าย | Catalog stock และจำนวนที่สั่ง | กัญจน์ | ผลจ่ายเต็มหรือเหตุผลที่ปฏิเสธ พร้อมประวัติ |
| รายการเตือน | ยาที่จ่ายเต็มและข้อมูลผู้ป่วย | กลอง | รายการเตือนในเว็บและผลที่ผู้ป่วยกดบันทึก |
| ข้อความ/Dashboard | ข้อมูลที่โมดูลอื่นบันทึกแล้ว | เฮิร์บ | Broadcast และข้อมูลสรุปตาม role |

ตารางนี้เป็นการจัดกลุ่มเพื่ออ่าน flow เดียวกัน ไม่ได้เพิ่มตาราง ผู้ใช้ หรือความสามารถนอก scope

## แผนที่ story กับเส้นทางโค้ดที่พบ

| Story | เส้นทางที่พบ | สถานะจากหลักฐานใน repository |
| --- | --- | --- |
| สมาชิก/โปรไฟล์ | `authService`, auth pages, `profiles` | มีโค้ด Supabase; ต้องตรวจ session/RLS จริง |
| แผนก/ตาราง | `ScheduleWorkspace`/`DepartmentWorkspace`/`DepartmentDetailWorkspace` → `SchedulingProvider` → mock หรือ `DatabaseSchedulingRepository` | มี route `/departments/[departmentId]`, ชิปวันลา edit/cancel และทั้งสอง adapter; ยังไม่ยืนยันว่า production ใช้ DB ครบทุกคำสั่ง |
